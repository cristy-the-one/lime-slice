# STEP editing, the kernel crate

`docs/step-modeler-evaluation.md` is the decision. This note is the contract for the first change: a kernel crate that dynamically links Open CASCADE Technology 7.9.2. Model mode, picking, measure, and the edits themselves are later changes. `crates/lime-slice-core` is not part of this work.

## What this change is

`crates/lime-model` is the swap point. `Kernel` is the trait. `open()` loads a session.

`OCCT_ROOT` selects the install. When it is set, the build links `TKernel` with `cargo:rustc-link-lib=dylib` and `open()` returns the string from `OCCT_Version_String_Complete()`. When it is unset, the C++ compiler is not run and `open()` returns an error. A static archive of `TKernel` fails the build.

The core, the `lime-slice` CLI, and the Tauri shell do not depend on this crate. Opening the app and slicing a file stay on the path they have today. Truck remains the reader of an unedited STEP file. An edited solid, when that exists, will tessellate into the existing `sourcePos` / `encodeStl` path.

`tools/occt/install.py` compiles tag `V7_9_2` as shared libraries. The pin, the archive URL, and the SHA-256 are in `third_party/occt/NOTICE.md`. The toolkit list is the modeling set through `TKMesh` and `TKShHealing`, plus `TKDESTEP` so Model mode can read a solid. CMake pulls `TKXCAF`, `TKV3d`, and `TKService` for that reader. FreeType and OpenGL stay off, and those toolkits build without them. STEP write is still a later change.

`tools/occt/stage_bundle.py` copies those shared libraries and the three notice files. The release workflow stages them at `src-tauri/resources/occt` and passes `src-tauri/tauri.occt.json`, which bundles that directory as `occt/`. A local `tauri build` does not pass that overlay and does not need OCCT. The staged directory is gitignored.

## How the libraries are linked

The link is dynamic on every platform.

- Linux: `libTKernel.so`, rpath `$ORIGIN`.
- macOS: `libTKernel.dylib`, install name `@rpath`, rpath `@executable_path` and `@executable_path/../Resources/occt/lib`.
- Windows: import library `TKernel.lib` at link time, `TKernel.dll` at run time.

`LIME_REQUIRE_OCCT=1` makes a missing library a test failure. The test reads the dynamic imports of its own executable (`ldd`, `otool -L`, or the PE import table) and requires `TKernel` there. CI runs that test on Ubuntu, inside the existing Rust job, and on `windows-latest` and `macos-latest`. The Ubuntu job is one of the required checks. The other two are not, so a merge waits for them on purpose.

The notices shipped beside the libraries are `third_party/occt/LICENSE_LGPL_21.txt`, `OCCT_LGPL_EXCEPTION.txt`, and `NOTICE.md`. The source offer is the official archive plus `tools/occt/install.py`, for at least three years after a release that includes the libraries. The rest of Lime Slice stays MIT. No GPL code is linked. SolveSpace is not a dependency.

The Intel macOS installer is the existing cross compile from the Apple silicon runner. That job builds the OCCT dylibs with `CMAKE_OSX_ARCHITECTURES=x86_64` and stages them. The native macOS CI job is arm64. The shell still does not link OCCT, so a missing dylib cannot stop the app from starting.

## Model mode

The fourth workspace tab is Model. It is not selected when the app opens. Shortcut `4`. Shift+4 stays the By layer strategy.

`crates/lime-model-occt` is a cdylib. It links the modeling toolkits and, when `libTKDESTEP` is present, the STEP reader. `crates/lime-model-load` dlopens that library. The CLI and the Tauri shell depend on the loader only, so a missing bridge cannot stop the app from starting. The shell looks beside the executable and in `occt/lib` under the resource directory. `LIME_OCCT_BRIDGE` overrides the path.

Model mode opens the object's STEP as the root of its history tree (`open` on `POST /api/model/tree`, or the `model_tree` command; see "History tree" below). The reply is the solid's tessellation, volume, face areas, and edge polylines. A STEP of surfaces with no closed solid replies `solid: false`: the readout says it can be measured but not edited, shows no volume, and every tool but Measure is off. A click selects one face or edge and reports its area or length. Shift-click adds or removes a pick. Exactly two picks report the distance. Escape, or a click on empty space, clears the selection. Edits open from the toolbar and run on Apply, which closes the tool. The tool's ghost in the view is a local stand-in; the result drawn in the solid's place while a tool is open is the kernel's dry-run ("The preview"). With no solid to show (an empty plate, or a selected object that is a mesh), the view says so in a card in its middle, with New solid and Open a file, and draws every plate object grey; see "New solid". Nothing is invented when the bridge is missing.

With more than one object on the plate, the others are drawn grey where they sit in model space (below). They are not part of any pick, snap, handle drag, framing, bed centring, or size readout, and no tool targets them but Boolean on an object, which picks its tool among them ("Booleans between objects"). The canvas carries `data-context-count` and `data-context` (each object's id and model-space box), `data-solid` (the open solid's model-space box), `data-context-screen` and `data-solid-screen` (their screen boxes), and `data-camera` for tests.

## Model space

Model draws every object in one shared frame, model space, apart from the plate layout that prints them (`src/model-space.ts`). The plate pose (orient, offset, placement scale, Arrange) plays no part in it, and nothing done in model space changes the plate, the mesh, or the slice.

- **Pose.** Each plate object has `modelPose`, a rigid pose from its own CAD frame into model space (an `Affine`; only a Separate-shells piece of a scaled part carries a scale, and those are meshes Model does not open). Absent is identity: an imported STEP or STL sits at its own file coordinates, so parts exported from one CAD assembly line up as designed, and unrelated files can overlap or sit far apart.
- **Seat.** The slicer lowers every mesh onto Z = 0 when it reads it. The amount, the mesh's seat, is kept by mesh token (`meshSeat`), so model space puts the mesh back up into its CAD frame before the pose. An STL's seat is known when the app reads it; a STEP or 3MF the slicer reads (`/api/mesh`, or the desktop's `preview_mesh`) comes back with `seatMm`, how far the reader lowered it; a mesh Model writes for a step or a split piece knows its solid's lowest point. So every import, and every piece Separate into plate objects cuts from one, sits at its file's own coordinates in model space from the start. An engine from before `seatMm` leaves a STEP's seat unknown, counted as 0 until Model first shows that object and learns it from the solid; pieces Separate cuts from such a file before then keep that 0 for good, since Model never opens a piece. A 3MF from such an engine keeps 0 for good too, since Model does not open a mesh. A Model-edited part, whose plate mesh is an STL saved already lowered, from a file saved before seats existed is learned the same way as such a STEP. A seat is taken only once its read still applies: a read that a newer Open, Add, or selection overtook changes nothing.
- **Split.** A split piece takes its parent's pose, so it sits exactly where it was cut, and the parent's other half sits right under or over it. On the plate both pieces still land on the bed in one spot, and Arrange lays them side by side.
- **Duplicate.** A copy takes the source's pose moved along model X by the source's own model-space width plus 10 mm (`DUPLICATE_GAP_MM`), so it sits beside the original instead of inside it. The plate pose is copied as before.
- **Separate shells.** Each piece keeps the place it had inside the part.
- **Tools.** Every number a tool takes or a handle drags is in model space: the Boolean primitive's origin and turn, the Hole's origin and axis, the Split plane, the Measure points. Before an engine call `toSolidOp` turns the op into the open solid's own frame with the inverse of its pose. A box or cylinder turns about its centre, so that centre goes through the inverse pose and the turn takes the pose's turn. With an identity pose, as in every file saved before this, the op is the one typed, number for number. Stored ops, probes, replay, and `.lime` trees stay in the solid's frame. The axis triad and the dock arrows are model space. A part with a local workplane (`docs/local-workplane.md`) has Boolean's and Hole's origin, Boolean's turn, and Split's X, Y and Z in its U, V, W instead, one step before `toSolidOp`.
- **History labels** name a step in the part's own frame, from the stored op alone, so moving a part later never renames its steps and a saved or replayed op labels as it did. With no pose the label shows the number typed. A Split typed along model Z on a part raised 10 mm reads "Split at Z 5"; on a part lying on its side it can land on another axis of the part ("Split at Y 15"), and on a part turned 30° about X it is a tilted plane of the part ("Split at Z 17.32, tilt −30° / 0°").
- **Place** (toolbar, Shift+P) moves and turns the open object in model space. X, Y and Z are how far its centre sits from where its file put it; Turn X, Y and Z turn it about that centre, in the order a primitive turns. The dock arrows and rings drag them. A field changes only itself: the other fields keep the pose's exact values, not the rounded ones shown, so a move never turns the part and never nudges another axis. A turn field keeps the other two angles as the pose has them, except within a hair of Turn Y ±90°, where X and Z share one turn and the other angle can shift while the part turns as typed. A field cleared or half typed moves nothing until it holds a number. Place runs on surfaces with no closed solid too, has no Apply, and its button reads Done. A Place gesture (one drag until the pointer lets go, or a typed or scrubbed number once it rests 400 ms) is one step: while Place is open, Undo and Redo (the buttons, Ctrl+Z, Ctrl+Shift+Z, Ctrl+Y) step its moves, and the solid's history waits until it closes. A gesture that ends where it began is no step. Each step is also a Prepare step, folded into the visit like an edit, so Prepare undo takes back a visit's moves with its edits. It is not a Model history node, because a node is a kernel op the engine replays per solid, and the pose belongs to the plate object rather than to any one step of its solid. History shows it instead in its Position row, which opens Place and resets the pose ("History panel").
- **Bed.** The bed and build volume are drawn faintly as a size reference, centred under the open object with the plate at its lowest point in model space, as before. They do not take part in model space, and the grid moves rather than being rebuilt as the part moves. The size chip and its fit warning read the part's own box, since where the part sits or turns in model space does not change what prints. The Bed button in the toolbar hides and shows them, and the choice stays for that browser (`localStorage`).
- **Camera.** Model frames the open object, in model space, from the front right and above, the first time it shows that object. A new solid of the same object (an Apply, a jump, Undo) keeps the user's view. Reset view (the button at the head of the size chip and readout column, under History, or Home) goes back to that framing; Shift+click or Shift+Home frames every object. The Objects list's Frame frames that object in Model and stays in Model. All of them share one framing function.
- **Cost.** Each grey object's matrix is composed when the plate or the open object changes, never per frame; the meshes keep their buffers and move by a matrix. The open solid's model-space box is computed once per solid and pose and shared by every tool, handle and note.
- **Saved.** `.lime` keeps `modelPose` (`{m, t}`) and `meshSeatMm` on each object, both optional. A file without them opens at identity. A pose that is not a turn times one uniform scale (a shear, a mirror, a collapse) is a damaged file. One object with a pose is written as version 2.

## New solid

A solid can start from a primitive instead of a file: on an empty plate, with an STL selected, or with another solid open. It becomes a plate object of its own, with a history tree of its own whose root is the primitive, so no file is read. From then on it is a solid like any opened STEP: every tool, History, Place, the STEP button, slicing through the plate commit, Duplicate, and `.lime` save and reopen.

- **Where it starts.** New solid is the first button of the Model toolbar, always there (Shift+N), because that bar is where Model's actions are. While a solid's tools fill the bar it shows its icon only, with its name in the tip, as STEP, Undo, Redo and Bed always do, so the bar still fits at 1440 px with Shell, Check, Workplane, and a pick's chip. With no solid to show, the card in the middle of the view offers it as its main button, beside Open a file (Add a file once the plate has objects, so the card never replaces them); the readout stays empty then, rather than repeat the card. The card gives way to any open tool, and shows only while nothing can be opened: never while a STEP is read or after an engine error.
- **The panel** is the Boolean tool's: the same primitive buttons (a row of icons, each named in its label and tip, arrow keys move between them), the same size fields and their scrub and drag knobs, the same ghost code. It has no origin and no turn, since the solid places itself, and its Apply reads Create. The note says where it lands. Create asks the engine once; a size the engine refuses goes to the readout with the panel still open.
- **Primitives**: box, cylinder, sphere, ellipsoid, cone, torus, wedge, polygon prism, and tube, with the fields of the table under "History tree (engine)". The Radius field is named for what it is on each (Bottom radius, Ring radius, Outer radius), and Across flats or Across corners follows the polygon's toggle, Flats by default since that is how a nut pocket is sized. Sides drags in whole numbers. No other OCCT primitive earned a place: `BRepPrimAPI_MakeHalfSpace` is what Split already does, a sphere segment (a dome) is a sphere and one Split, and `MakeRevol` or a free `MakePrism` need a profile, which the engine's extrude and revolve ops take ("Extrude, revolve, and shell").
- **The root** is the primitive standing centred over its own origin, its lowest point on Z = 0, untilted (`rootSpec` in `src/model-primitive.ts`), so its own frame is a printable one. It keeps only the fields its kind reads; the rest are 0. The engine builds it on `open` from `primitive`, and again on every replay, checking it against the root's fingerprint; a root that builds differently says so in its own words, since the root cannot be dropped. A size within 1e-6 mm of 0 is 0 to the engine (a hole that thin is a solid tube), and a size that must be there and is that small is refused.
- **Where it goes.** In model space it stands at the origin when model space is empty, else beside everything, as Duplicate puts a copy: along +X, 10 mm (`DUPLICATE_GAP_MM`) past the farthest object, centred on their Y, on their floor (`newSolidPose`). The open object counts as the view shows it, edits not yet on the plate included, so the ghost stands exactly where Create puts it. On the plate it goes where an added file goes, the first clear shelf slot, or centred on the bed when the plate is empty. Its plate mesh is its tessellation as an STL, as for an edited step.
- **The name** is the primitive's and the first number no object has with it: Box 1, Box 2, Cone 1 (`primitiveName`). The root's History row names the primitive and its sizes: "Cone ⌀20 to ⌀8 h 30".
- **Undo.** Creating is a Prepare step, folded into the Model visit like an edit: Prepare undo takes the visit back, the object with it, and its tree stays while redo can bring it back. A solid created on an empty plate leaves an empty plate again; only a step taken before any file was loaded (`meshless`) empties the plate, so a step taken while a file is still being read never does.
- **The view.** With nothing open, opening New solid looks at where the solid will land, and so does a settled number or a picked primitive that grows it out of view; while a number is typed or dragged the view stays put. Create opens the new solid and frames it.
- **Cost.** The ghost is built on the client from the sizes alone, and only when a size changes (`primitiveMesh`); its shaded and edge geometry are built once per mesh, so a move or a turn only moves them. Nothing asks the engine until Create. Each plate mesh's own box is read once. The new solid's STEP is written as an edited step's is, on leaving Model, at a save, or by the STEP button, and is kept as its `brep`, so an app without primitive roots still opens the part; the tree itself never reads it.
- **A copy** (Duplicate) of a new solid on its root starts from the same primitive, with no STEP written or read, even once the root has a STEP.

## Parameters

Parameters is a panel, not a toolbar button. It opens from the Features ▾ menu (Parameters) and with Ctrl+Alt+P. The toolbar stays the same width, so it still fits at 1440 px. The panel is a table: name, value or expression, the evaluated number, and how many steps on the open solid use that name. Add, Delete, Up, and Down change the table. Parameters evaluate in order, so a later name may use an earlier one. A bad name, a duplicate, or an expression the evaluator refuses is written on that row, in the evaluator's words, and later rows still see the earlier names that worked.

Every number in a Model panel accepts an expression, such as `wallH / 2 + 1`, with the same evaluator (`src/modeling/expr.ts`). While the field is focused it shows the expression. Otherwise it shows the number, with a small ƒ when the text was an expression. Apply stores the number on the op. The text is kept in the optional `exprs` field and is dropped before any engine call, so a request with no expression is unchanged. The same ƒ is on a heads-up size, a sketch driving dimension, a push/pull distance, and an edge drag's radius. A sketch stored on an op keeps each dimension's expression.

Changing a parameter lists the steps on the shown branch whose stored numbers no longer match, as "Rebuild 1 step" or "Rebuild 3 steps". Rebuild replays from the earliest of those steps, as one edit. Undo returns the solid to the previous numbers. The parameter table stays at the new value.

The table is the optional top-level `parameters` field of a `.lime` file. An older file with no such field opens unchanged.

## Booleans between objects

The Boolean tool fuses, cuts, or intersects the open solid with another plate object as well as with a primitive: a split piece, an import, or a New solid. The owner asked for it on 2026-10-15, and decided that it asks per op and that the tool object leaves the plate unless "Keep the tool object" is ticked.

- **The panel.** Boolean's choice of what it combines with is its primitive row: a primitive, as before, or Object, the row's last button (New solid does not show it). It stays one tool rather than a second one, since the op, the Fuse / Cut / Common buttons, the dry-run and Apply are the same, and the toolbar has no room to spare at 1440 px; and Object sits in the row rather than in a Primitive / Object switch of its own, so the panel gains no row: at 1280 × 640 History keeps room for its rows under the open panel, and the phone sheet still shows a row of fields above its buttons. Picking a primitive again goes back to it. Shift+G opens Boolean on an object (G stays Boolean; Shift+G was free in every scope). With Object chosen the primitive's fields hide, and a short list names the other plate objects that can be the tool; a click on a grey object in the view picks it as well. A click on a grey object that cannot be the tool says why in the readout ("cube.stl is a mesh, so it cannot be a tool."). The pick is drawn as the ghost, where it sits in model space, from the grey object's own buffers moved by its matrix and flat-shaded as the grey objects are, and it is no longer drawn grey; its outline is found once per mesh, and not at all past 150 000 triangles, where finding it would hold up the pick. Under Fuse, Cut and Common is "Keep the tool object", off whenever Boolean opens and after each join, since the owner asked for the choice per op. The readout says what will happen: "Cut telo split from telo.stp; telo split leaves the plate.", "Fuse Box 1 into telo.stp; …", "Intersect telo.stp with Box 1; …", Intersect as the History label says it. The note under the panel carries the dry-run as for a primitive. No handle drags the tool; Place moves it, on its own.
- **What is offered.** Only solids: an object Model has opened as a solid, or a STEP, a New solid or a copy of one that it can open. A mesh (STL, 3MF) is not offered, nor surfaces with no closed solid once Model has seen them; an object picked before Model opened it gets its tree then, and if it turns out to be surfaces it leaves the list with the reason in the readout. The open object is never its own tool. A tool whose history already uses the open solid (it joined it, at any depth) is refused with "The tool object's history already uses this part, so the two cannot be joined." The refusal is per tree, not per step: two trees that each named the other could neither be closed nor have that join's branch deleted, since the engine keeps every tree and step a join names. So the brief's narrower case (a tool step that itself depends on the open solid) is refused, and so is a step that does not, which is the price of that rule.
- **Op.** `{kind: "join", op: "fuse" | "cut" | "common", tool: {object, key, node, name}, relative: {m, t}, keepTool}`. `tool.key` and `tool.node` name the tool object's tree and the step its plate mesh is, at Apply. `relative` is the tool's pose in the target's own frame, the target's inverse model pose then the tool's (`relativePose` in `src/model-space.ts`, built by `joinOp` in `src/model-request.ts`), worked out once at Apply and stored, so moving either object later never moves a cut already made. A tool whose tree moves on after Apply keeps the step the join named.
- **History.** The join's row is a merge: the steps that made its tool come in on a lane of their own, can be looked at, and can be edited from there ("A tool's steps in History").
- **Labels** come from the stored op: "Cut telo split", "Fuse Box 1", "Intersect Sphere 1". The tool's name is captured at Apply (`tool.name`), not looked up, because the tool usually leaves the plate, where there is nothing to look it up on, and because a label must read the same after a rename, a save, or a replay, as every other label does.
- **Engine.** `apply` and `probe` take the join; the engine builds the tool's step from its own tree (its kept solid when it holds one), places it by a location built from a unit quaternion, so nothing is copied and the location carries no scale, and runs the boolean as for a primitive. `relative` must be a turn and a move, within 1e-6: a scale, a shear or a mirror is refused with "The tool's placement must be a turn and a move only, with no scale, shear, or mirror". Replay of a target's join asks the tool tree for its step, so one tree's step depends on another's. A tool tree or step the engine does not hold answers `{error: "The tool object's history is not open in the modeler", missingTool: {key, node}}`, with `broken: id` when a step of the tree asked about cannot be built for it; nothing is marked, so once the client opens that tree the same call works. `close` refuses a tree that a join in another tree takes its tool from, and `drop` a branch with such a step. A join's `keepTool` and its tool's `object` and `name` build nothing, so a probe and an Apply that differ only there share one build.
- **Plate.** With Keep off, Apply takes the tool off the plate in the visit's Prepare step, the one that holds the target's change, so Prepare undo puts it back with its pose, paint and tree key. An Apply of the same join from the same step, which shows the step it built before, takes the tool off too. Undo in Model above the join leaves the tool wherever the plate has it, and the plate taking the join's step again never takes the tool off: only Apply does, since taking an object off the plate behind the user's back would surprise more than leaving one there. A split piece fused or cut back into its own part in the same visit stays off the plate when the plate takes that step, rather than come back as a split's piece does.
- **Trees.** A tree stays while a join names it, on the plate or not (`reachableTrees`), and the client closes trees each before the trees its joins take a tool from (`closeOrder`), one at a time in one queue, as the engine requires; a close the engine refused goes again after the next. A tree from a project that sits on its STEP-read step is numbered from that step in the engine, so before a call that could build a join naming such a tree's root (a join on the way to the step asked for, the join being applied, or theirs in turn), that tree is opened whole; a join naming any other step of it gets `missingTool`. An engine that answers `missingTool` gets that tree back from its root and ops, once for every call that found it missing at once, and the call goes again; a split piece's tree rebuilt after a restart does the same for its joins. A tool tree that does not come back marks nothing in the client either.
- **Save.** A join names its tool by object id and step, without the engine key. The tool's tree is saved whenever a saved join names it: with its object if that is on the plate, else in `modelTools: [{id, name, modelTree}]` at the top of the file, under the id the join names. On load every tree is adopted after the trees its joins take a tool from (`toolFirst`); the engine opens each when a call first needs it, the tool's when the target's join asks for it (`missingTool`), so a tool's tree is always whole in the engine before a join builds from it. A tree whose join's tool tree is missing or damaged, in the file or in its bytes, is left out, with the notice a damaged tree gets, and so is any tree that took a tool from it; a kept tool no saved join names any more is dropped quietly. A save whose tool tree cannot be written leaves the target's tree out and names it in the notice after the save. A file without joins is written and read as before; an older app reads a join as an unknown op, so it leaves that tree out with its notice and opens the part from its mesh.

## Shipping the bridge

The release workflow builds the cdylib after staging the Open CASCADE libraries and copies it into `src-tauri/resources/occt/lib`, next to those libraries. The cdylib's rpath is `$ORIGIN` on Linux and `@loader_path` on macOS.

On Windows the exe (through the vendored Clipper2 C++) and every Open CASCADE DLL link the Visual C++ runtime dynamically: `msvcp140.dll`, `vcruntime140.dll` and `vcruntime140_1.dll`. A PC without Visual Studio or the VC++ Redistributable has none of them, and the app stops at start with "MSVCP140.dll was not found". The release workflow runs `tools/windows/stage_crt.ps1`, which copies the three DLLs from the runner's Visual Studio redistributable folder into `src-tauri/resources/crt`. It then also passes `src-tauri/tauri.crt.json`, which puts them beside the exe. Microsoft allows this app-local copy. The exe's own folder is the first one Windows searches, both for the exe and for the bridge (`LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`). For a local installer, run the script and add `--config src-tauri/tauri.crt.json`.

## Booleans and a plane split

Model mode can fuse, cut, or intersect the open solid with any primitive New solid offers (box, cylinder, sphere, cone, torus, wedge, polygon prism, or tube), and it can split the solid with a plane. The numbers are millimetres in model space; the engine gets them in the solid's own frame ("Model space"). A kernel failure is the readout, and the solid is left as it was. There is no mesh boolean behind it.

An edit is a new node in the object's tree; the plate takes it when it commits ("History tree (client)"). The plate's mesh for an edited node is the settled tessellation, written with `encodeStl` under a `.stl` name, so truck is not asked to read the edited solid. The pose stays. Support paint, seam paint, and support edits start empty on a node the plate has not held, because they named another surface; going back to a node the plate held puts its paint back. A split keeps the piece on the negative side of the plane and adds the other piece in the parent's place at once, with the same pose, so the two halves are not parked side by side. Both settle onto the bed, so the plate lists them as overlapping and offers Arrange. The second piece is the root of a tree of its own (the engine's `otherKey`), so selecting it opens it in Model with no STEP read, and it can be edited and split again. Undo above the split leaves the piece on the plate.

### The split plane

The Split panel picks the plane's base with X, Y, Z, or Face (`src/model-plane.ts`, pure math in whatever frame it is given). `splitState` in `src/app/model.ts` works the plane out in model space, and `toolOp` takes it into the solid's own frame for the engine ("Model space").

- **X, Y, Z** cut square to that axis. They are the axes the view's triad and the dock's arrows show, which are model space: the view draws the solid's tessellation at its model pose. With an identity pose, as for every file not moved in Place, that is the solid's own frame, so the triad's X is the solid's X and the op's X. The number is the plane's coordinate on that axis in model space, through the solid's centre line. On a local workplane X, Y and Z are its U, V and W, and the line is the axis through the frame's origin (`docs/local-workplane.md`). A picked face is taken into model space by the pose the same way. The solid's extent along the normal, and the extent of its own box's corners that the kernel checks, are both measured along the normal turned back into the solid's frame and moved by the pose, so the window is the kernel's at any turn.
- **Face** cuts parallel to the last picked face, and turns Face picking on whenever it is chosen or Split opens in it. The number is the offset into the part, from the area-weighted middle of the face. A face whose corners leave its plane by more than 0.001 mm is curved and is refused with "Pick a flat face. This one is curved."
- **Tilt A and Tilt B** turn the normal, in degrees, A about the base plane's first in-plane axis u and then B about the second, v. u is the world axis after the base normal's nearest one (X → Y → Z → X), made square to the normal, and v = n × u: a Z plane tilts about X then Y, an X plane about Y then Z, a Y plane about Z then X. The plane turns about its pivot, the point where the base line crosses it, so a tilt does not move the cut away from where it was put. A typed tilt past ±85° is held at ±85°, in the field once it is left and in the plane at once. Split opens untilted, and a new solid starts untilted, since a tilt was about the part it was set on.
- The op is only `{origin, normal}`: the pivot and the turned normal. It names no face, so a replay never depends on face numbering.
- The note gives the legal range of the number and its middle, and a new base puts the number in the middle. A plane is legal when it stays the margin (2 %, at least 0.25 mm) inside both the solid's own extent along the normal and the extent of its bounding box's corners along it, which is how the kernel measures it (`split_reject`), and 0.001 mm more, since the kernel measures its box from the B-rep with tolerance and the pieces' 0.25 mm floor along the normal. That floor reads each piece's vertices first and, only when they show less, its exact surface box: half a torus, a sphere, or a cylinder cut along its axis has every vertex in the cut plane, and was refused as too close to a face (`tests/primitives.rs`). On Telo test the floor costs what it did. On an axis the two extents are the same. Each extent is measured once per solid and normal, and the plane once per panel state, so typing a position measures nothing and one keystroke works the plane out once. `tests/kernel.rs` checks the kernel cuts 0.001 mm inside its margin and refuses 0.001 mm outside it.
- Labels come from the stored origin and normal alone, in the part's own frame ("Model space"), so a saved split reads as it did: the world axis the normal is nearest, where the plane crosses that axis, and the tilts from it, "Split at Z 42, tilt 15° / 0°". When both tilts round to 0° the label is the axis alone, "Split at X 10", so a float32 normal a hair off an axis still reads as that axis. The crossing is a property of the plane, not of its pivot, so two different planes never share a label, even past 45° where the nearest axis changes. A face split reads the same way, from its normal; the offset from the face is not in the op, so it is not in the label.
- X, Y, Z, and F are not Split shortcuts: X is Scale in Model, Y the front view, and F Lay flat. Split's key is D. P is Push/Pull.

## Fillet, chamfer, hole, and scale

Model mode can fillet or chamfer the picked edge, cut a cylindrical hole, and scale the solid by one factor. The blend size, the hole radius, and the hole depth are millimetres. Scale is about the solid's centre.

### Fillet and chamfer

Fillet and chamfer open once an edge is picked. The button stays disabled until then, and its tip says to switch to Edge and click the edges. Inside the panel, **Edges** chooses which edges the step blends:

- **Picked** is the edges clicked on the solid, as before. Shift-click adds another. The size is millimetres, typed or dragged on the first edge.
- **A step** is every sharp edge one history step made that is still on this solid. The step is the one on screen when A step is chosen. A click on a history row of this solid, or of a step above it, chooses that step instead, and so does the list or the step number. A row of another solid, or a step that is not this one or above it, is refused in the readout and the view stays. **All**, **Convex**, or **Concave** keeps every sharp edge, or only the ones that bend out or in. The line under the choice reads "Edges of: Roof (convex)". The engine call `stepEdges` names those edges on the solid on screen, and the view outlines them. The size handle sits on the first of them. Apply sends one pick, `edges: [{fromNode, filter}]`, the same pick the MCP sends. `filter` is omitted when it is all.

Editing such a step opens the panel on A step, with that step number and "Edges of: <row> (<filter>)". A blend whose edges were picked opens on Picked. A blend that mixes a step pick with a picked edge, or that names two steps, opens on Picked with the picked edges: the panel edits one step at a time.

### Hole

The owner asked on 2026-10-15 whether Hole only goes straight down and so duplicates a Boolean cut with a cylinder. It does not: it drills into a face, and it knows Through all and a counterbore, which a cylinder cut does not. A countersink was not asked for and is not offered.

- **Where it drills.** The hole starts at the origin fields and runs into the face picked last, along its inward normal; with no face picked it runs straight down (−Z in model space), or along −W on a local workplane, and an edited step keeps the direction it was applied with until a face is picked. Hole opens in Face picking so a click on the solid picks one, and the note says which it is: "Into the picked face.", "Straight down; click a face to drill into it.", "Along −W; click a face to drill into it." on a tilted workplane, or, for an edited step, "As the step drilled; click a face to drill into another."
- **Through all** (a box under the fields) cuts to wherever the part ends along the axis. The op stores `through: true`, never a length, so a replay after an earlier edit (a taller root, say) still goes all the way: the kernel works the length out once per build from the solid it cuts, the farthest corner of its bounding box along the axis plus 1 mm (`reach_along`, `kThroughMarginMm`). The Depth field is disabled and its knob gone while the box is ticked, and Depth keeps its number for when it is not. The ghost runs the same length, worked out the same way in the solid's own frame from its tessellation's box, read once per solid (`throughLength` in `src/model-hole.ts`); on a curved part that box can differ from the kernel's by the chord.
- **Counterbore** (a second box) adds a wider, shallow bore at the entry: Bore radius and Bore depth, each with a knob. The kernel fuses the two coaxial cylinders into one tool and cuts the part once, so the part's volume is still integrated once per op (two builds: the fuse and the cut). It refuses, in these words, a counterbore no wider than the hole ("The counterbore must be wider than the hole"), a depth not above 0 ("The counterbore needs a positive depth"), and one as deep as the hole or deeper ("The counterbore must be shallower than the hole"): as its plain depth, or with Through all as far as the part reaches, within 0.001 mm. Through all or the plain depth still applies to the hole itself. A through hole with no radius is "A hole needs a positive radius", since it reads no depth.
- **Screw** is a list that fills the fast path: a medium clearance hole of ISO 273, Through all, and a counterbore for an ISO 4762 socket head cap screw, the head's diameter plus 1 mm and its height plus 0.4 mm, so the head sinks just below the face with room for a printed part. It shows the screw the numbers are, else Custom, which only shows.

| Screw | Hole ⌀ | Counterbore ⌀ × depth |
|---|---|---|
| M2 | 2.4 | 4.8 × 2.4 |
| M2.5 | 2.9 | 5.5 × 2.9 |
| M3 | 3.4 | 6.5 × 3.4 |
| M4 | 4.5 | 8 × 4.4 |
| M5 | 5.5 | 9.5 × 5.4 |
| M6 | 6.6 | 11 × 6.4 |
| M8 | 9 | 14 × 8.4 |

- **Op.** `through`, `counterboreRadius`, and `counterboreDepth` are optional and absent when off, so every older op, `.lime` file and probe key reads and keys as before. They are scalars, so `toSolidOp` carries them as they are. Labels: "Hole ⌀5 depth 8", "Hole ⌀5 through", "Hole ⌀3.4 through, counterbore ⌀6.5 × 3.4". A saved counterbore with only one of its numbers, or a `through` that is not true or false, is a damaged tree.
- **Holes from sketch points.** In a sketch on a face, select points or circle centres and press H, or use the sketch card's Holes button. H does this only while a sketch is being edited; with no sketch open, H is still the Hole tool. The Hole panel opens with "One hole at each of N points." and hides the origin fields, because each hole sits on its point. Radius, depth, Through all, and Counterbore apply to every hole, and each of those can be typed or dragged. Apply stores one group of hole steps. `source` is `{kind: "sketchHoles", sketch, points, radius, depth, through?, counterboreRadius?, counterboreDepth?}`: the sketch as it was, and the point ids in step order. The kernel stores `source` and does not build it. The history row reads "3 holes ⌀4 depth 8" or "1 hole ⌀3.4 through, counterbore ⌀6 × 3.2". A kernel refusal names the step ("Step i of n: …") and that hole is drawn red. A hole that misses the solid is still skipped, not refused. History Edit reopens this panel. There is no toolbar button. While the sketch is open the canvas carries `data-sketch-holes` (`off`, or how many). A sketch on a plane or the bed says "Sketch on a face to place a hole at each point." Nothing selected says "Select points or circle centres." Esc closes the panel and stays in the sketch.

### The dry-run

Fillet and chamfer stay disabled until an edge is picked, and the button's tip says how to pick one. Once the tool is open, A step needs no further edge click: Apply waits on the step and the dry-run. While the numbers change, a dry-run builds the fillet, chamfer, hole, shell, or boolean on a copy and leaves the solid alone. A number being typed or dragged waits 300 ms (`PROBE_WAIT_MS`, sized to typing speed so one number asks once); a number settled with Tab or by leaving its field, opening a tool, a pick, the end of a drag, and every other one-off change ask at once. One check runs at a time: a check asked while the engine still builds one waits for it, and only the newest goes, so numbers typed field after field never queue a whole edit each. Answers are kept by tree node and numbers (`probeKey`), since a node's shape never changes: undo back to a checked node enables Apply at once. Apply, undo, and redo ask nothing. The numbers just applied leave Apply off, since applying them again would change nothing. The note says it works, or why not, and for a blend the largest size that did. Apply stays off until that check passes. Split and scale are judged from their numbers. The desktop shell runs every Model command off the UI thread. A kernel failure is the readout, and the solid is left as it was. There is no mesh fallback.

A dry-run that works keeps the shape it built; an Apply of the same op on the same node commits that shape instead of building it again. Each resulting shape's volume is integrated once, by the op that made it, and reused for the reply; a scale multiplies the volume by the factor cubed.

### The preview

Every tool shows its result while it is open, as Scale always did; the owner asked for it on 2026-10-16, since only Scale did and that was not consistent.

- **Boolean, Hole, Shell, Fillet, Chamfer** (and an edited step of these, and a join): the dry-run asks for its shape (`probe` with `preview`), and the shape it built is drawn in the solid's place, coloured as the solid is. The solid stays under it, hidden, so a click still picks the solid the tool works on, and its picked faces and edges stay outlined over the shape. As in Fusion's preview, a Boolean keeps its tool's translucent outline over the result, which says where the cutter is; the Hole's cylinder and the blend's tube give way to the shape once it is checked, since the shape shows the hole or the round itself and a stand-in over it would hide it. Shell draws no stand-in at all: the checked shape is the hollow. Faces that will be removed are outlined in the danger colour, dashed, over that shape; a shell kept closed ignores the picks and draws them as an ordinary selection. While new numbers are checked (the 300 ms wait, then the kernel) the shape just checked stays and the stand-in comes back over it, so a drag answers at once and the exact shape follows. A check that fails shows the solid as it is, with the reason in the note, as before. The handles stay throughout.
- **Scale** keeps its own preview: the solid drawn scaled about its centre, which is exact for one factor and needs no kernel.
- **Split** builds nothing while it is open, and needs no shape: both pieces keep all the material, so the result is the solid itself with a cut. It shows the two parts it makes instead: the solid is clipped at the plane, the side the part keeps drawn as it is, and the side that becomes a part of its own drawn tinted, over the plane itself. Clipping planes on the GPU, so nothing is built or meshed.
- **Cost.** The probe meshes its shape once, at the chord Apply uses, and the shape keeps what it measured and meshed; an Apply that takes the probe's shape meshes and measures nothing again (`meshes` does not move; `tests/join.rs`). So Apply costs no more than before, and less. The four shapes used last are kept by node, numbers (`probeKey`) and chord, so going back to numbers just checked draws their shape without asking; an answer whose shape left those four is asked again, since the shape is what is shown. The 300 ms wait stays.

**Apply ends the tool.** After an Apply the tool closes: no ghost, panel or handles stay, and Cancel is never needed to put a tool away. Undo takes the step back. Opening the tool again starts from the numbers applied last, for the session, so a run of similar steps stays quick: the fields keep their values, as they always did between tools, and only Split goes back to the middle of the part, untilted, since the part it was set on was just cut. Numbers already applied on the step shown leave Apply off, as before. Edit step's Update closes the same way. Place, Workplane, and Check have no Apply and keep Done.

`lime_model_occt::stats()` gives the linked Open CASCADE `version` and counts builds, volume integrations, `tessellations` (replies built rather than taken from the reply cache), `meshes` (shapes meshed), and `descriptions` (shapes whose faces and edges were measured for a reply) for `tests/kernel.rs` and `tests/tree.rs`.

## Features

Pocket, Boss, Texture, Array, Ribs, and Text share one toolbar entry, **Features**, with a menu. The button shows the last one used and keeps it for the next session. Each tool needs exactly one flat face; any other selection says "Pick one flat face." Texture, Array, and Ribs cover that face's whole coplanar plane. The panel's fields are the MCP schema's, under the same names: a pocket or boss is a rect, circle, or arch (width and height, or a diameter), a depth, and a position on the face typed as U and V or dragged, from the centre, a corner, or the middle of the bottom or top edge. A pocket can leave bars across it. Texture is lines, grid, brick, or shingle, with a pitch along U and V, a groove width, and a depth. Array repeats a rect, circle, or polygon cell, with its size, turn, pitch, stagger, angle, margin, fit (the whole cell, or its centre), and raise or cut. Ribs run along U or V, with an angle, a width, a pitch or a count, a depth, a margin, and raise or cut. Text takes the letters, a height, a stroke, a spacing, centre or start, an angle, a depth, and raise or engrave, placed on the face.

Apply stores one group (`{kind: "group", label, source, steps}`). The row is the label ("Pocket 10 × 10, 2 bars"). `source` is the spec that was typed, so Edit step reopens that tool on the parent solid and expands it again; Update replaces the node. A group with no feature, pattern, or mirror source still has no panel. The ghost draws every piece. Past 2,000 pieces it draws outlines only. A dry-run that refuses a step highlights that piece in red and frames it. Depth drags along the face normal, the position drags on the face, and pitch drags along U and V; every other number has a knob too, and every number can be typed. The expansion is the shared one (`expand` in `src/modeling/compose.ts`, the face frame in `src/modeling/frames.ts`), so the panel and MCP build the same pieces from the same solid.

These edits commit as a boolean does. Pose stays, except that a scale sets the plate's `partScale` back to 1 so the part is not scaled twice; going back to a node the plate held puts its placement scale back.

## Pattern and mirror

Pattern and Mirror repeat history steps. They live in the Features menu, on the same button as Pocket and the other composites, so the toolbar still fits at 1440 px. Several selected faces also offer both on the selection bar; those buttons click the same menu items. The button shows whichever of them was used last. Ctrl-click (Cmd-click) history rows of the open solid to choose the steps; the tool opens on the step on screen, unless that step is the root. A click without Ctrl still shows that step. A row of a tool object's lane says "A pattern repeats a step of this solid." The chosen rows carry an accent bar. Only a Boolean of a primitive, a hole, or a group of those can be repeated. Anything else says "Only a Boolean, a hole, or a feature can be repeated." A step named in `source.of` that is no longer in the history says "A step this repeats was deleted."

Pattern is linear, polar, or along a path. Linear takes a step X, Y, Z and a count, and an optional second direction when its count is above 1. Polar takes a count, an axis (X, Y, Z, or a picked edge or cylinder or cone), a centre, and an angle. The centre starts at the solid's centre. Path takes points, from a click on the solid or from the point fields and Add point, a count, and Align. Mirror takes a plane X, Y, or Z through a point (the solid's centre when the tool opens), or a picked flat face, and Keep the original. Every number can be typed or dragged: arrows move a step or a point, knobs change a count or the angle, and a dot sits on the centre, the path point, or the plane point.

Apply stores one group. `source` is `{kind: "pattern"|"mirror", of: [node ids], ...fields}`, the same fields the MCP pattern and mirror use. The count includes the original, so the group's first copy sits on the step that is already in the history; cutting that copy again does not change the volume, and the volume matches the same cuts made one at a time. Keep the original off undoes the source steps with the opposite boolean (a cut becomes a fuse, and a fuse a cut) and then adds only the mirrored copies, because those source steps stay in the history. A common cannot be undone that way ("Keep the original on for a common."). A blind hole becomes the cutting cylinder it drills, along its axis, and a counterbore a second shorter wider cylinder. A through hole has no fixed length ("Holes cannot be patterned yet."). A wedge cannot be mirrored. Edit step reopens the panel from `source`. The motions are `patternMotions`, `pathMotions`, `mirrorMotion`, and `movedSpec` in `src/modeling/compose.ts`.

## Extrude, revolve, loft, and shell

The engine builds four ops that boxes and cylinders cannot: a profile pushed or turned, and a hollow. A gable roof of any pitch, with overhangs at the eaves and the gable ends, is one extrude. Shell has a panel, after Hole. An extrude, a revolve, or a loft made from a sketch is edited from History: the pencil reopens that sketch and the feature, and Apply replaces the step and replays what was under it. A loft reopens every section it was picked from. A sweep is that same loft, and Edit reopens its profile and its path. A face extrude or a move of faces still has no panel ("This step has no edit panel yet. Delete it and apply it again with new numbers."). A step above any of them can be edited, and it replays. A shell step opens in the Shell panel.

- **The profile** is a closed outline of `[u, v]` points, at least 3, on a plane. The plane is a workplane's frame (`docs/local-workplane.md`): `origin`, and `turn` about X, then Y, then Z, whose columns are U, V, and W. No `turn` is the model axes. The last point joins the first; a repeat of the first at the end is dropped. Either winding builds the same solid. The kernel refuses, in these words, fewer than 3 points ("A profile needs at least 3 points."), two points in a row in one place ("Two profile points in a row are in the same place."), sides that cross or touch ("The profile crosses itself."), and an outline with no area ("The profile has no area."). Within 1e-6 mm two points are one.
- **Loops** replace that point list on an extrude, a revolve, or a loft section: `loops`, the first the outline and the rest holes. Each loop is `{start: [u, v], segments: [...]}`. A segment is `{kind: "line", to: [u, v]}`, `{kind: "arc", through: [u, v], to: [u, v]}` (the circle through the three points), or `{kind: "spline", through: [[u, v], ...], to: [u, v]}`. The loop must end where it starts, within 1e-6 mm. The outline turns one way and each hole the other (`ShapeFix_Face` as well). Give `profile` or `loops`, not both ("Give a profile or loops, not both."). An open loop is "A loop is open. Its end must meet its start." Loops that cross, or a hole that crosses the outline, are "These loops cross." A hole outside the outline is "A hole lies outside the outline. Keep each hole inside." An arc whose three points are in a line is "An arc's three points are in a straight line. Move the middle point off that line." `smooth` and `corners` belong to a point profile ("smooth and corners are for a point profile. A loop uses arc and spline segments."). A loft section takes a radius, a profile, or loops, and every section of one loft needs the same number of holes ("Each loft section needs the same number of holes."). The field is absent when unused, so an older op and an older file read as before.
- **Extrude** `{kind: "extrude", op, origin, turn, profile, depth, symmetric?, depth2?, draftDeg?, upTo?}` pushes the profile `depth` along W, or along −W when it is negative, or `depth` in all centred on the plane with `symmetric: true`. A depth of 0 is "An extrude needs a depth other than 0." The prism is always swept along +W from its lower end, so it comes out the right way round (`BRepPrimAPI_MakePrism`). `depth2`, above 0, is the distance on the other side of the plane: the prism runs from −`depth2` to `depth` when `depth` is positive, and from `depth` to `depth2` when `depth` is negative. It is not combined with `symmetric` ("An extrude is centred, or it has a second depth, not both."). `draftDeg` leans the walls. A positive angle makes the section smaller as W increases, by `distance × tan(angle)` on each side; on a one-sided extrude the far end is the smaller one, whichever way `depth` points, and a square stays a square. A negative angle grows that end, and the convex corners of the outline are rounded as they grow. On a two-sided or centred extrude the wall is one plane at that angle, so a positive angle shrinks the +W end and grows the −W end. The angle is built with `LocOpe_DPrism` using the height `BRepFeat_MakeDPrism` would ask for (`height / cos(angle)`), then fused, cut, or intersected like a plain extrude, because that feature's own fuse rewrites the solid it is given. An angle at 89° or beyond is "A draft angle must be between -89 and 89 degrees." One that pinches the profile shut before the depth is "This draft closes the profile before the depth. Use a smaller angle or a shorter depth." `upTo` is a face of the solid this step is built on. A fresh pick is a face index; the stored op names it `{index, mid, areaMm2}`, and a rebuild finds it again as a shell finds an open face. The prism stops where it meets that face (`BRepFeat_MakePrism` against the face's plane). The face has to be flat ("An extrude can stop on a flat face. This face is not flat."). `depth` only chooses the direction and may be 0, which goes along +W. The extrude starts at the profile, so a second depth or a centred extrude is refused ("An extrude up to a face starts at the profile. Drop the second depth." and "An extrude up to a face starts at the profile. Leave centred off."). A draft that also stops at a face is not built ("A draft up to a face is not available yet. Drop the draft, or drop the face and set a depth."). A direction that misses the face is "The extrude does not reach that face. Move the profile so its direction meets the face." A second depth that is not above 0 is "The second depth is a distance on the other side of the plane, above 0." A second depth, a draft, or a face to stop at is for a point profile. Each of these fields is absent when it is off, so an older extrude is the same op it was. An extrude that came from a sketch also keeps optional `sketch` (`"v": 1`, the drawing). The kernel never reads it: every engine request drops it, and the client puts it back on the op the engine echoes. A sketch that never became a feature is not saved. A missing or unreadable `sketch` is ignored and the extrude still opens, so an older file is unchanged. When a second depth, a draft, or a face to stop at is set and the region is one outline of straight lines, the request sends a point `profile` instead of `loops`, because the kernel refuses those fields on loops. An arc, a spline, or a hole with one of those fields is refused in the client with "A second depth, a draft, or a face to stop at is for a point profile." and is not sent. Equal sides are `symmetric` and stay on loops.
- **Revolve** `{kind: "revolve", op, origin, turn, profile, axisOrigin?, axisDir?, angleDeg?}` turns the profile about the in-plane line through `axisOrigin` ([0, 0]) along `axisDir` (V, [0, 1]), by `angleDeg` (360) (`BRepPrimAPI_MakeRevol`). The profile may touch the axis and must keep to one side of it ("The profile crosses the revolve axis. Keep it on one side."). The angle is above 0 and at most 360 ("A revolve needs an angle above 0 and at most 360 degrees."); an axis of no length is "The revolve axis needs a direction in the profile's plane." A solid the turn leaves inside out is turned the right way. A revolve that came from a sketch also keeps optional `sketch`, the same drawing an extrude keeps, stripped before the engine sees it and put back on the echo. A missing or unreadable `sketch` is ignored, so an older revolve opens unchanged.
- **Smooth profiles.** `smooth: true` draws splines through the points instead of straight edges (`GeomAPI_Interpolate`), one closed spline when `corners` is absent. `corners` lists the indexes of points that stay sharp: a spline runs from each corner to the next, and two corners side by side are a straight edge, so a revolve's edge along its axis is two corners. The profile is checked as its straight outline. A corner not on the profile is "A corner is not the index of a profile point." Both fields are absent when off.
- **Loft** `{kind: "loft", op, sections, ruled?}` builds a solid through `sections` in order, two to 200 (`BRepOffsetAPI_ThruSections`, smooth, or flat between sections with `ruled`). Each section has `origin` and `turn`, as a profile's plane, and is a circle of `radius` about the origin, an ellipse with `radiusV` along V (`radius` along U), a `profile` with its `smooth` and `corners`, or `loops`. A section that does not build names itself ("Section 1: A profile needs at least 3 points."). A loft through sections in one plane has no volume and is refused ("The loft has no volume: its sections lie in one plane."); one that folds through itself is "The loft twists through itself. Space the sections further apart, or make tight bends gentler." A loft that came from sketches also keeps optional `drawing`: `sketches`, one drawing per section (null when the section is a face), and `sweep` when the loft was a sweep (`profile`, optional `pathSketch`, `path`, `scale`, optional `edges`). The kernel never reads `drawing`: every engine request drops it, and the client puts it back on the op the engine echoes. A missing or unreadable `drawing` is ignored and the loft still opens, so an older file is unchanged. A sweep is not a new kernel op. The client samples the path and places copies of the profile as these sections (`src/modeling/sweep.ts`, one section per sample, `steps` 1). U is carried forward, so the profile does not twist. `scale` is one number or one per path point, the same fields the MCP `sweep` takes. There is no twist field. A corner that turns more than 25° is refused before anything is sent ("This path has a sharp corner. Fillet the corner, or draw a smooth arc. A sweep that follows the corner is not available yet."). The profile is the region's outer outline only; a hole in it is not swept. A later kernel sweep can follow the real wire with `BRepOffsetAPI_MakePipeShell` and `BRepBuilderAPI_RightCorner` at a sharp corner. That is not built: the loft of profile copies is the solid for a smooth path, and a sharp corner is refused rather than lofted into a bad solid.
- **Combined.** All three are fused with, cut from, or intersected with the solid by `op`, as a boolean's tool, with its refusals. Two more: an extrude or revolve that leaves the volume as it was ("The extrude does not change the part.", "The revolve does not change the part."), and a fuse that leaves a body apart from the part, which says how far apart ("This would add a separate body 2.00 mm from the part. Move it that far toward the part, plus a little overlap.") or that it only touches ("This would add a body that only touches the part, at a face, an edge, or a point. Push it further in so the two overlap."). The op is stored as sent; the absent fields stay absent.
- **Shell** `{kind: "shell", thickness, openFaces?}` hollows the solid inward to walls `thickness` thick, with the faces `openFaces` names removed (`BRepOffsetAPI_MakeThickSolid`, joined by intersection so inner corners stay sharp, and by arcs when Open CASCADE cannot intersect the walls). No face open leaves a closed void: the part's shell and its inward offset, one solid of two shells. The Shell panel, after Hole, types the thickness or drags one knob: along the first picked face's inward normal, or docked while no face is picked. The open faces are the current face picks, listed as a count ("2 faces open"). "Keep it closed (hollow inside)" ignores those picks. There is no ghost; the dry-run's shape is the hollow, and faces that will open are drawn with a dashed outline. A fresh pick is a face index of the parent's reply, as `faces_find` reports it; the stored op names each face as `{index, mid, areaMm2}`, its centre of area and its area, and a rebuild finds it by those as a blend finds its edges. Edit step re-picks those faces (`matchFaces`) before the panel's snapshot, so Update stays off until the thickness or the faces change. Refusals: "A shell needs a wall thickness above 0.", "That face is not on this solid.", "A shell needs at least one face left closed.", "Shell works on a part of one body.", "This part is hollow already.", and, when Open CASCADE fails or the result is not a valid solid smaller than the part, "This wall is too thick for the part's smallest feature."
- **Edges from a step.** A fillet's or chamfer's `edges` may also hold `{fromNode, filter?}`: the edges step `fromNode` made or changed that are still on the solid blended. The Fillet and Chamfer panels send that pick from **A step** ("Fillet and chamfer"). `stepEdges {key, node, filter?}` answers the indexes of those edges on the tree's current solid, which is how the view outlines them before Apply. `filter` is `all` (the default), `convex`, or `concave`, and each keeps only sharp edges, since an edge already smooth, or a seam, cannot be blended (`ChFi3d::DefineConnectType`). The step's edges are the edges of its solid that are not on the solid it was built from: an edge an op leaves alone keeps its shape in Open CASCADE's result, so this is what the builder's Modified and Generated history names, read for every op alike. The root made every edge it has. They are read once from the step's solid, by midpoint and length, and found on the solid blended the same way, at every build, so an edit above the step, or a replay from saved nodes, finds them again. The op keeps the pick as sent, beside any index or reference picks. The step must be the blend's parent or above it ("A blend can only take edges from this step's parent or a step above it."); a step that left none of the kind is "Step 3 left no convex edges on this solid to fillet." An edit replays steps under new ids, so the client renames a replayed blend's `fromNode` to its step's new id (`renumberedSteps`).
- **Face extrude** `{kind: "faceExtrude", face, distance, draftDeg?, upTo?}` builds a prism on `face` along its outward normal (`BRepPrimAPI_MakePrism`), fused when `distance` is positive and cut when negative. A positive prism of a flat face is started 0.001 mm inside the solid so the fuse overlaps instead of only touching. `draftDeg` (absent when 0) drafts the sides (`BRepFeat_MakeDPrism`, the angle in degrees). `upTo` stops the prism at another face (`BRepFeat_MakePrism` `Perform`); the distance then only picks the direction. The face is stored as `{index, mid, areaMm2}` and found again as a shell's open face is. Refusals: "A face extrude needs a distance other than 0.", "The draft angle must be between -89 and 89 degrees.", "A face cannot stop at itself.", "That face is not on this solid.", "This face has no direction to extrude along.", "Push or pull works on a part of one body.", "The face extrude does not change the part.", and, when Open CASCADE cannot build it, "Open CASCADE could not extrude this face."
- **Move faces** `{kind: "moveFaces", faces: [{face, distance}]}` offsets each face along the solid's outward normal and lets the neighbours extend or trim (`BRepOffset_MakeOffset`, `SetOffsetOnFace`, skin mode, intersection join). Every other face is offset 0. Pulling a box's top makes the box taller. On a hole wall the solid's outward normal points toward the hole's axis, so a positive distance makes the hole smaller and a negative distance widens it. The last distance wins when one face is named twice. A distance of 0 refuses the whole step. Refusals: "Pick a face to move.", "A face move needs a distance other than 0.", "That face is not on this solid.", "Push or pull works on a part of one body.", and, when Open CASCADE cannot offset the faces, "This face cannot move with its neighbours here. Push or pull adds material instead: hold Alt."
- **Face loops** `faceLoops {key, node, face}` reads one flat face and answers `{id, face, origin, turn, loops}`. `loops` are D2 loops in the face's plane: the first is the outer boundary, wound counter-clockwise, and the rest are holes, wound clockwise. Each loop has `start: [u, v]` and `segments` of `{kind: "line", to}`, `{kind: "arc", through, to}`, or `{kind: "spline", through, to}`. A full circle is two semicircle arcs, because a three-point arc cannot close on itself. `origin` is the face's centre of area and `turn` is the workplane a face click would set (`workplaneOnFace`), so a loop can be placed as a loft section later. Refusals: "Face loops are for a flat face." and "Open CASCADE could not read this face's outline."
- **Labels:** "Extrude 3-point profile 30 both ways", "Cut extrude 4-point profile 10", "Extrude 4-point profile 10 and 4", "Extrude 4-point profile 10, draft 5°", "Cut extrude 4-point profile up to a face", "Revolve 4-point profile 360°", "Extrude 2-loop profile 5", "Loft through 6 sections", "Cut loft through 2 sections, ruled", "Sweep along 4 points", "Cut sweep along 4 points", "Shell 2, 1 face open", "Shell 1, closed", "Fillet convex edges of node 2 r 1", "Pull face 5 mm", "Push face 3 mm", "Move 2 faces 1.5 mm". A face extrude adds ", draft 4°" or ", up to a face" only when that field is set.
- **Model space.** As for every op, the numbers are the solid's own frame. `toSolidOp` takes a profile's plane through the pose like a primitive's frame: its origin moves, and its turn takes the pose's turn. A loft's sections each move so. A face pull's distance is the same in any pose, so `toSolidOp` leaves `faceExtrude` and `moveFaces` as they were typed. `extrudeOp`, `revolveOp`, `loftOp`, `shellOp`, `faceExtrudeOp`, `moveFacesOp`, `faceLoopsRequest`, and `stepEdges` in `src/model-request.ts` build the ops as the engine stores them.
- **Push/Pull (P), and the gesture when no other Model tool is open.** Hover a face: it lights, and a small arrow sits at the pointer along the outward normal. The readout says "Drag to push or pull · Alt: add material · double-click: repeat 5 mm" once a distance has been made, or "the last distance" before that. Dragging maps the pointer to a distance along the normal (`src/push-pull.ts`, `src/interact/drag-axis.ts`). With nothing else held the step is `moveFaces`, so the neighbours follow: a box gets taller. Alt on one face is `faceExtrude`, a prism on that face only. Several faces, Shift-clicked first, always `moveFaces`, each along its own normal by the same distance, even with Alt. Ctrl snaps to whole millimetres, other faces' heights snap with a dotted line, and a double-click repeats the last distance and the last mode. While the pointer moves, a client prism is drawn (`facePrism`); after it has been still for 300 ms the kernel previews, and no probe is asked while the pointer is moving. Release applies at once, one undo step. The readout then says "Pulled 5 mm · Tab to edit" (or "Pushed" when the distance is negative). Tab within 3 seconds reopens the heads-up distance on that step and Enter edits it (`edit`), it does not apply a second step. The panel's Distance field (`modelPull`) does the same move with Apply, always `moveFaces`. A cylindrical face's description carries `radiusMm`, `surface`, and for a cylinder or cone `axisPoint` and `axis`; the heads-up shows the resulting diameter when exactly one cylinder is in the drag. On a boss the outward normal points away from the axis, so a positive distance grows the diameter. On a hole wall it points toward the axis, so a positive distance shrinks the hole. History Edit (Shift+E) still has no panel for these steps. The 3-second Tab is the edit. The toolbar button is an icon, named Push/Pull in its tip, so the bar still fits at 1440 px beside Shell, Check, Workplane, and a pick's chip. `src/push-pull-ui.ts` owns the gesture.

- **The selection bar.** A click on a face, an edge, or empty space opens a small bar by that click (`#modelContextBar`). It sits 24 px clear of the pointer, and off the solid, the toolbar, the readout, the size chip, History, the measure labels, and the view cube, so it never covers the thing being edited and those messages never cover it. It fades after 3 s still and comes back when the pointer returns to the selection. Tab moves between its buttons and Enter runs the focused one. Each button clicks the same toolbar button, and its tip shows that shortcut. One flat face offers Push/Pull, Hole, Sketch on face, and Shell (open this face). Several faces offer Move faces, Shell (open these), Pattern, and Mirror. A cylinder offers Change diameter, which is Push/Pull: the Distance field is the offset, and the drag still shows the resulting diameter. A cone or a sphere offers Push/Pull. Edges offer Fillet and Chamfer. Empty space offers Sketch on bed and New primitive: the button opens New solid, and the menu picks the primitive, whose sizes are typed in the panel. Sketch on face sits after Hole and Sketch on bed sits before New primitive, so the face bar's arrow keys still move from Push/Pull to Hole. The bar hides while a tool panel is open and while a face or an edge is dragged. Escape closes that panel and the bar returns; Escape with no panel open clears the selection. The canvas carries `data-selection-bar` with the kind (`flat-face`, `faces`, `cylinder`, `curved`, `edges`, `empty`). Pocket, Boss, Text, Paste, Hole through an axis, Use as an axis, and Section are not on the bar until those tools exist. Pattern and Mirror register themselves with `registerContextAction` from `src/model-repeat.ts`. Sketch on face and Sketch on bed register from `src/app/sketch.ts`. The bar reads that list and does not keep its own.

- **Where a probe's new hollow or piece is.** A probe that builds a solid with more solids or shells than its parent adds `voids` (each a closed shell inside a solid that is not its skin and was not there before, as a box `{min, max}`) and `pieces` (each body beyond the largest, as a box with `volumeMm3` and `gapMm`, its distance to the largest) to its measures (`piece_report`).

`tests/sketch.rs`, `tests/extrude_extent.rs`, `tests/loft.rs`, `tests/loops.rs`, `tests/shell.rs`, `tests/faces.rs`, and `tests/feature_edges.rs` check each volume against one worked out by hand, each refusal, and a replay. `extrude_extent.rs` is the second depth, the draft (a 5° frustum on a 10 mm square pushed 10 mm), and an extrude up to a slanted face. `tests/loops.rs` is a washer (a circle with a circular hole) and a rounded rectangle, each against its exact area times the depth, and the refusals for an open loop, crossing loops, and a hole outside the outline.

## History tree (engine)

The bridge also keeps Model history as a tree: one tree per plate object, one node per edit, and a new edit from an older node starts a branch instead of dropping the newer steps. The client owns node ids, labels, and which branch Redo follows. The engine keeps what is costly to rebuild. The kernel operations are in `cpp/kernel.cpp`; the tree's nodes are built with them in `cpp/tree.cpp`.

Every call is one JSON request through `lime_occt_tree` (`POST /api/model/tree`, or the `model_tree` command). `call` picks the operation. `key` names the tree, and node 0 is its root.

| `call` | Fields | Answer |
|---|---|---|
| `open` | `key`, one of `dataB64` (a STEP file, or a solid `export` wrote in `brep`), `stepPath`, `box: [x, y, z]`, `primitive` (a primitive, as below), or `feature` (an extrude, a revolve, or a loft built alone, fuse only); `chordMm`; optional `nodes: [{id, parent, op, fingerprint}]` (parents first) and `current`; optional `fingerprint`, the root's as saved; optional `seed: {node, dataB64}`, one saved step's solid in `brep`; optional `quiet` | The reply for `current` (default 0), or with `quiet` only `{id, fingerprint, replayed}`: the step is built and kept, not meshed. Saved nodes are registered, not built. A `seed` gives its step that solid, so the step and the steps after it build from it, not from the root ("Saved solid"); a seed that does not read, is STEP, or does not match its step's fingerprint is left out, the step is replayed instead, and the answer adds `seedRefused` with why. Opening an existing key replaces that tree. A root that builds to another fingerprint answers `{error, broken: 0}` and opens nothing. |
| `apply` | `key`, `parent`, `node`, `op`, `chordMm`; `otherKey` for a split | The new node's reply, plus `op` as stored (edge picks resolved) and, for a split with `otherKey`, `other`: the root reply of a new tree under that key. A split without `otherKey` (a replay) sends no piece and does not tessellate it. Applying an existing node with the same parent, op, and `otherKey` is a jump to it; anything else on an existing id is refused. |
| `probe` | `key`, `node`, `op`; optional `preview: true` and `chordMm` | `{ok: true, volumeMm3, solids, shells, before}`, or `{ok: false, error, maxMm?}`: the edit was built on a copy, or why not and, for a blend, the largest size that fits. `volumeMm3` is the built solid's volume, `solids` its separate bodies, and `shells` its closed shells (a hollow body is one solid of two); `before` is `{volumeMm3, solids, shells}` of the solid probed, so a caller reports the change without building it again. The volumes are the ones the ops integrated, so the measures cost two shape counts. A group adds `skipped` (how many of its steps missed the solid) on a build that works, and `failedStep` (counting from 1) on one that does not ("Group"). With `preview`, a build that works also answers `preview`, the built shape's reply at `chordMm` ("The preview"). A probe that works is kept, and an Apply of the same op on the same node commits it, meshing nothing the preview meshed. |
| `edit` | `key`, `parent`, `node`, `op`, `replay: [{id, op}]`, `chordMm`; optional `tools: [{key, parent, node, op, replay}]` | An edited step ("Editable history"): `op` built on `parent` as the new `node`, then each of `replay` on the last that built, in one call, under one lock. The reply is the last step that built, plus `built: [{id, op, fingerprint}]` (each step kept with its solid, its op as stored) and, when a replayed step did not build, `broken: {id, error}`: that step is kept, marked broken, with the rest of `replay` unbuilt under it. Only the last step that built is tessellated. A kept probe of `op` on `parent` is reused, as by Apply. When `op` itself does not build, or a join names a tool tree the engine lacks (`missingTool`), nothing is kept. With `tools`, a tool's step edited from this tree's history ("A tool's steps in History"): each entry is one tool tree's part, deepest first, built the same way before this tree's, and each part after the first, and this tree's `op`, must be a join naming the tip (the last id) of the part before. A tool tree or parent the engine lacks is `missingTool` before anything is built. A tool part whose replay breaks is kept broken, and so is the join it fed, which has no tool to take ("The tool object's step could not be rebuilt: …"), with that tree's replay unbuilt under it; this tree then shows the join's parent. When a part's own `op` does not build (the edited step, or a join whose tool built), nothing is kept in any tree. The reply adds `tools: [{key, built, broken?}]` in the order sent. |
| `goto` | `key`, `node`, `chordMm` | That node's reply. |
| `drop` | `key`, `node` | `{dropped, current}`. The node and everything under it go; the current node moves to the parent if it was inside. The root cannot be dropped, nor a branch with a step another tree's join takes as its tool. |
| `close` | `key` | `{ok: true}`, or a refusal while another tree's join takes its tool from this one. |
| `distance` | `key`, `node`, `aKind`, `aIndex`, `bKind`, `bIndex` | `{id, distanceMm}`. |
| `faceLoops` | `key`, `node`, `face` (an index, or `{index, mid, areaMm2}`) | `{id, face, origin, turn, loops}`: the flat face's outline in its plane ("Extrude, revolve, loft, and shell"). |
| `stepEdges` | `key`, `node`, optional `filter` (`all`, `convex`, or `concave`; absent is all) | `{id, node, edges}`: indexes on the tree's current solid of the edges step `node` made that the filter keeps ("Fillet and chamfer"). The caller shows that solid first, so `id` is the solid on screen. A step that is not in the history is "Step N is not in this history." A step that is not the current solid or above it is "A blend can only take edges from this step's parent or a step above it." A step that left none of that kind is "Step N left no convex edges on this solid." |
| `export` | `key`, `node`; optional `format`: `step` (the default) or `brep` | `{bytesBase64, byteLength, format}`: AP214 STEP of that node, or its solid in Open CASCADE's binary format ("Saved solid"). |

`open` reads STEP so that facet shells that sew into closed solids open as solids, and surfaces that do not open for measuring only. On such a root every `apply` and `probe` answers the refusal ("This STEP file has surfaces but no closed solid, so it can be measured but not edited.") before anything is built.

`op` is one of `{kind: "boolean", op, ...primitive}`, `{kind: "hole", origin, axis, radius, depth, through?, counterboreRadius?, counterboreDepth?}` ("Hole"), `{kind: "split", origin, normal}`, `{kind: "fillet" | "chamfer", edges, size}` (an edge may be `{fromNode, filter?}`, "Extrude, revolve, and shell"), `{kind: "scale", factor}`, `{kind: "join", op, tool, relative, keepTool}` ("Booleans between objects"), `{kind: "extrude" | "revolve", op, origin, turn, profile, ...}` or `{kind: "loft", op, sections, ruled?}` or `{kind: "shell", thickness, openFaces?}` or `{kind: "faceExtrude", face, distance, draftDeg?, upTo?}` or `{kind: "moveFaces", faces}` ("Extrude, revolve, loft, and shell"), `{kind: "group", label, source?, steps}` ("Group"), or `{kind: "root", ...primitive}`: a new solid's primitive built again from other numbers in place of the solid above, which is how an edited primitive root forks ("Editable history"). A `root` step is refused anywhere but right under the root.

### Group

A group is one history node for several edits: `{kind: "group", label, source?, steps}`. `label` is the row's name ("Pocket 10 × 10, 2 bars"). `source` is the composite as it was typed, kept so an edit can reopen it, and never built; it is absent when the group was not typed as a composite, and two groups with the same steps are the same step whether or not `source` differs. A `source.kind` of pocket, boss, texture, array, ribs, or text reopens that tool ("Features"). A `source.kind` of pattern or mirror reopens that tool ("Pattern and mirror"). A `source.kind` of `sketchHoles` reopens the Hole panel ("Hole"). A group of sketch extrudes, or of sketch revolves, has no `source` and every step is that one kind; Edit reopens the sketch. Any other group still has no panel. `steps` are built in order, each on the shape the one before left.

A step may be a boolean, an extrude, a revolve, a loft, or a hole. A fillet or a chamfer may too, when every edge is named by its place (`{index, mid, lengthMm}`) or by an earlier step (`{fromNode, filter?}`), not by a bare number. A split, a join, a scale, a shell, a face extrude, a face move, a new solid, or another group is refused with a sentence that names the step: "Step 2 of 3: A group cannot contain a split." The first step that fails refuses the group the same way, and the sentence is that step's own with "Step i of n:" in front. The answer is `{error, failedStep}`, on a probe and on an apply. A step whose tool misses the solid is left out and counted, not refused: a hole that misses, a common that does not overlap, an extrude, revolve, or loft that does not change the part, and a boolean the kernel accepts whose volume is unchanged. The probe then answers `skipped` as well as the usual measures, and `pieces` or `voids` when the whole group, against its parent, left a hollow or a separate body. A group with no steps is refused. Replaying a group builds its steps again and checks the group's fingerprint. `.lime` stays version 3: `source` may be absent, and a file from before groups open unchanged.

A feature root is that extrude, revolve, or loft on `open`'s `feature`, with `op` fuse and no solid under it: the tool is the solid. Cut and intersect are refused ("A new solid is the extrude itself. Cut and intersect need a part that is already there.", and the same for a revolve or a loft). Any other op is refused ("A new solid starts from an extrude, a revolve, or a loft."). `feature` is sent only for such a root, so an open of a STEP or a primitive is the same request as before. `feature` never carries `sketch`, and a loft's `feature` never carries `drawing`. Editing an extrude, a revolve, or a loft root reopens its sketch, then replaces node 0 and reopens the tree from the new feature; the old root fingerprint is not sent, and child fingerprints are cleared first so a child is not marked rebuilt differently. Node 0 stays. A sweep root is that same loft, and Edit reopens the profile and the path. Several regions of one sketch are a group of extrudes or of revolves, and that group is not a feature root ("A new solid is one extrude." or "A new solid is one revolve.").


A primitive is `{primitive, origin, turn, ...}` in millimetres, with the fields its kind reads. Every kind but a sphere turns about its centre by `turn` (degrees about X, then Y, then Z). The newer fields are stored only when sent, so a box, cylinder, or sphere op reads and stores as it did before they existed. The engine checks every size and answers a refusal in plain words ("A cone needs a height above 0", "The tube's inner radius must be smaller than its outer radius", "A polygon needs 3 to 64 sides"); `tests/primitives.rs` lists them all.

| `primitive` | Fields | Sits | Built with |
|---|---|---|---|
| `box` | `size` | from `origin` along +X, +Y, +Z | `BRepPrimAPI_MakeBox` |
| `cylinder` | `radius`, `height` | `origin` is the bottom centre, up +Z | `BRepPrimAPI_MakeCylinder` |
| `sphere` | `radius` | `origin` is the centre | `BRepPrimAPI_MakeSphere` |
| `ellipsoid` | `size` (full widths along X, Y, Z) | `origin` is the centre; it turns about it | a unit `BRepPrimAPI_MakeSphere` stretched by `BRepBuilderAPI_GTransform` |
| `cone` | `radius` (bottom), `topRadius`, `height` | as a cylinder. Either radius may be 0, not both; equal radii build a cylinder | `BRepPrimAPI_MakeCone` |
| `torus` | `radius` (the ring, to the tube's centre), `tubeRadius`, smaller than the ring | `origin` is the centre, the ring flat in XY | `BRepPrimAPI_MakeTorus` |
| `wedge` | `size`, `topX` from 0 to `size[0]` | as a box; the top face runs from `origin`'s X for `topX`, so 0 is a ramp and `size[0]` a box | `BRepPrimAPI_MakeWedge`, its narrowing axis laid along Z |
| `polygon` | `sides` (3 to 64), `across`, `flats`, `height` | as a cylinder, one flat facing −Y. `across` is the width across corners, or across flats with `flats: true`, as a nut is sized | `BRepBuilderAPI_MakePolygon`, a face, `BRepPrimAPI_MakePrism` |
| `tube` | `radius` (outside), `innerRadius`, smaller, `height` | as a cylinder. An inner radius of 0 is a cylinder | the wall's section turned once about the axis (`BRepPrimAPI_MakeRevol`): one solid, not a cut | A fresh fillet or chamfer may name edges by index. The stored op names each as `{index, mid, lengthMm}`, where `mid` is the point at the middle of the edge's parameter range. A rebuild takes the index when its midpoint and length still agree within 0.001 mm, else the one edge that matches them, else the node is broken.

A reply is the node's tessellation with `id` set to the node and `format: "lime-solid-2"`. The client reads no array from a reply without that format and says the modeler does not match the app (`src/model-reply.ts`). The bulk arrays are base64 of little-endian words, decoded straight into typed arrays that view the bytes in place:

| Field | Words | What |
|---|---|---|
| `positions` | f32 | Nine per triangle: a triangle soup, wound outward. |
| `triangles` | u32 | The face index of each triangle. |
| `edgePoints` | f32 | Every edge's polyline, one after another, three per point. |
| `edgeOffsets` | u32 | One more than the edges: edge `i` is points `edgeOffsets[i]` up to `edgeOffsets[i + 1]`. |

The client keeps all four as f32 and u32, so the words lose nothing it reads. The rest is JSON, since it is small and kept as f64: `volumeMm3`, `solid` (false for surfaces with no closed solid), `faces` (`{areaMm2, normal?}` by face index; `normal` is the outward unit normal at the face's middle), `edgeLengths` (by edge index), `fingerprint: {volumeMm3, faces, edges}`, `replayed` (how many steps were rebuilt to answer it), and `held` (the nodes of this tree that keep a solid). A reply may also carry `stepFaces`, one entry per face: the node that made that face. A preview puts `null` on a face the step being tried has not applied yet, and keeps the parent's node on a face it only inherited. A missing `stepFaces`, or one whose length is not the face count, is ignored, so an older engine still draws. The Open CASCADE version is in `lime_model_occt::stats()`, not in a reply. A missing tree answers `{error: "unknown", missing: [0]}` and a missing node `{error: "unknown", missing: [id]}`, so the client sends the root and the ops again. A step that fails to rebuild, or rebuilds to a different fingerprint, answers `{error, broken: id}`; that node and everything under it lose their solids and stay unbuilt until it is dropped.

What is kept, per node:

- The solid, with its face and edge maps and the volume the op integrated. Each tree pins its root, its current node, every eighth node on the path between them, and every seeded step, whose solid only a replay of every step above it could build again. The 24 most recently used other solids stay; older ones are evicted and rebuilt on demand from the nearest kept ancestor.
- The fingerprint, for as long as the node exists. Every rebuilt step is checked against it.
- The reply, per chord, as it is sent, for the 8 most recently viewed nodes across all trees. A jump to one of those does no kernel work; the bridge copies the cached reply once, into its answer, and the loader copies that answer out of the bridge.
- With the solid, from its first reply: its face areas and normals and its edge lengths, and the chord its faces were meshed at. A reply built again at that chord, for a jump to a node whose reply left the cache, neither integrates a face nor meshes again: 1 ms instead of 84 ms on Telo test. A step built on another takes the measures of every face and edge the two share (the booleans and blends run non-destructively, so an untouched face is the same face), so its first reply measures only what the step changed: 0.3 s to 1 ms on the 4707-face back cover. Faces are meshed, and measured, in parallel; each face's mesh and measures are its own, so the reply is the same as one thread's. Booleans run in parallel too, and a solid's volume is integrated face by face in parallel, about Open CASCADE's own point and added in its order, so it is the same number to the last bit. A step built on another solid meshes only the faces it made and the faces beside them, when every other face carries a mesh made at exactly the reply's chord: meshing the whole solid would keep those meshes, and would mesh the made faces against the same edges. A step that made more than half the faces, one whose other faces carry a mesh made at another chord (even a finer one), a root, a seeded step, and a split's other piece mesh whole. `tests/local_mesh.rs` builds booleans of each primitive, a hole, a fillet, a chamfer, a shell, a join, a split, a scale, and steps on a solid shown at another chord, both ways, and compares the replies byte for byte. On the back cover a step's mesh is 5 to 8 ms instead of 155 ms.
- An edge's midpoint and length, computed the first time a fillet or chamfer asks.

What is skipped: a rebuild tessellates only the node asked for, never the steps on the way. A split's other piece is tessellated once, for the apply that made it. Jumps never send it again, and replaying the split never touches the piece's own tree. Jumping above a split leaves both pieces in place.

Every call holds the tree's lock for its whole run, so tree calls run one at a time. Booleans and the split run non-destructively, so building a child or a probe never changes its parent's tolerances. Before 2026-10-18 they did not quite: each boolean was first built destructively and thrown away, and that run could raise tolerances or add curves on the parent's shared edges, which is why a solid saved then can hold more bytes than the same solid built now; the faces, edges, volumes and meshes are the same. The fuse that joins a split's pieces on one side is non-destructive too since then. STEP reads and writes take a lock of their own as well, because Open CASCADE keeps their settings globally.

## History tree (client)

`src/model-request.ts` builds every request the client sends, so a check against the real engine can build the same ones. `src/model-tree.ts` is the tree as data: nodes with their op, label, and fingerprint, `current` (what Model shows), `committed` (what the plate holds), and which child Redo follows. `src/app/model-trees.ts` keeps one tree per plate object, by the key the object carries as `modelTree`; the engine uses the same key.

- **Apply** sends `apply` with the shown node as `parent` and a fresh id, and shows the new node. From a node that has children it starts a new branch and Redo follows it; the old branch stays. Numbers already applied from this node jump to that step instead of building it again.
- **Undo** jumps to the parent and **Redo** to the child last applied or jumped through; the buttons, Ctrl+Z, and Ctrl+Y do this. At the root Undo is off, and Ctrl+Z in Model never reaches Prepare's history.
- **A jump** to one of the four nodes shown last draws the solid the client kept and asks the engine nothing. Any other jump asks `goto`.
- **The plate commits lazily.** Apply and jumps change only the tree and the view. The plate takes the shown node when Model closes, and before a slice, a G-code or 3MF export, a send to the printer, a project save, a switch to another object, a duplicate, or Arrange. Committing saves the paint, support edits, and placement scale of the node it leaves, and puts back those of the node it takes, if the plate held it before. A node the plate held keeps its mesh bytes, so going back to it gives the plate the same bytes, and a slice of them is found in the cache. Each Model visit that changed the plate is one Prepare step, and Prepare undo of it finds its node again by the mesh it restores, in any tree of that object. When the plate takes a node below a split whose piece a Prepare undo took off, the piece comes back.
- **A copy** of an edited object (Duplicate) gets a tree of its own, rooted in the STEP of the step it copies, in the primitive when it copies a new solid's root, or in the feature when it copies a sketch-started solid's root.
- **A forgetful engine** (a restarted `serve`) answers `{error: "unknown"}`. The client opens the tree again with the root STEP, the root primitive, or the root feature, and its fingerprint, and every saved op, then asks once more. A primitive or feature root that builds to another fingerprint is broken with everything under it, as a step is. A split piece's tree comes back by running its split again on a spare node of its parent tree, which is then dropped.
- **A broken node** (`{error, broken}`) is marked with everything under it; the readout says the step cannot be rebuilt, and the client does not ask for it again.
- **Release.** A tree stays while a plate object or a Prepare step can reach it as Model would find it: by its key; by a step whose plate mesh the object holds, in a tree of that object (after a Prepare undo to before the object had a key); for an object with no key, by any tree with its mesh (a copy finding the step it copies); and from each of those, the tree a piece was split from, the pieces its splits made, and the trees its joins take a tool from. Each time a Prepare step lands (which can push the oldest step out or clear the redo steps), the other trees are dropped here and closed in the engine. So a removed object's tree stays exactly as long as Prepare undo can bring the object back, or a join names it.

### Saved with the project

A project saves each plate object's tree as `modelTree`, next to its `brep` ("STEP save"):

```
modelTree: {
  nodes: [{ id, parent, op, name?, fingerprint, piece? }],   // root first, parents before children
  current, committed, nextId,
  rootStep: { name, bytesBase64?, byteLength, hash }   // or, for a new solid, exactly one of:
  rootPrimitive: { primitive, origin, size, radius, height, turn, ... }
  rootFeature: { kind: "extrude" | "revolve" | "loft", ... }   // a solid that started from a sketch
}
```

- `op` is the op as the engine stored it, so a fillet or chamfer keeps each edge as `{index, mid, lengthMm}` (a bare index only if the engine did not echo the op). An extrude may also carry optional `sketch`. The engine never stored that field; the client keeps it for History Edit. Labels are not saved; they come from the ops, and the root's from the object's name, or from a new solid's primitive.
- A new solid's tree keeps `rootPrimitive`, the primitive as the engine stores it, a few bytes instead of a STEP, and no `rootStep`. It is saved even with no step after its root, since there is no file to open it from again. A tree with both, or a damaged primitive, is a damaged tree. Files with `rootStep` read as before.
- A solid that started from a sketch keeps `rootFeature`, the extrude, revolve, or loft as stored, and no `rootStep` or `rootPrimitive`. It is saved even with no step after its root. A tree with more than one of `rootStep`, `rootPrimitive`, and `rootFeature`, or a damaged feature, is a damaged tree. Files with `rootStep` or `rootPrimitive` and no `rootFeature` read as before.
- `rootStep` is written once per tree. When the file already holds those bytes (the object's own mesh or `brep`, another object's, or an earlier root, as for a copy), it is written without `bytesBase64` and read from the record with the same hash and length. An imported STEP root is saved as the engine's binary solid of it ("Saved solid"), written once while the engine holds it, unless a plate object's file is still those bytes; `name` stays the file's, as History's root row shows it. The engine tells the two apart by their first bytes.
- A split piece's tree is saved with the STEP of its own root (written at save if Model has not written it), so it opens without the part it was cut from. A split names its piece by the piece's plate object id, and only while that object is on the plate and its tree is saved. If the engine cannot write the piece's root, that tree is not saved, a notice after the save names the part, and after a reopen its split no longer counts as having made a part.
- Saved: the tree Model would resume for the object's mesh (by its key, or the object's other trees as after a Prepare undo), when it has a step, a name, a piece that a saved split names, a primitive root, or a feature root. Not saved: engine keys, shapes, replies, broken marks, which child Redo follows, and the paint and meshes of steps the plate does not hold. Trees of objects that are no longer on the plate are not saved, but for a tool's that a saved join names (`modelTools`, "Booleans between objects").

On open, each tree gets a fresh key (`freshTreeKey`), so a file opened twice, or two files one after another, never meet in the engine. Nothing is sent until Model needs a step. A `brep` in the binary format (`isBrep`, told by its first bytes) is the plate's step exactly ("Saved solid"), so the first call opens the whole tree at once, quietly, at its root, with that solid as the plate's step's `seed`: one call, no step replayed, and the call that needed the tree then asks for its step. Every edit builds on it at once, a fillet's edge numbers included; a jump above it rebuilds from the root, counted in the readout when more than 20 steps need building (`countedReach`, from the steps the engine's last answer says it holds). A seed the engine refuses is said with the step when it shows ("The saved solid did not open (…), so its history was rebuilt."), and the solid is not sent again. A STEP `brep` (a file from before version 3, or one saved again before its history ever opened whole) opens as before. The plate's step opens from the object's `brep` alone, as a STEP file does, and the engine numbers it as its root (node 0) while the client keeps its own id: enough to look at it, measure it, and check an edit. A call on any other step, an edit of a step, and an Apply that names edges or faces first opens the whole tree: `open` with the root STEP, every saved op, and `current` set to that step, which the engine rebuilds from the root and checks against its fingerprint. Calls made while that open is on its way wait for it, and share it; a call sent before it but answered after it is asked again, since the engine need not run calls in the order they were sent. A new step placed by its numbers (a Boolean, a hole, an extrude, a split) builds on the read solid at once: the 2.6.1 back cover would otherwise rebuild 326 steps first. Its fingerprint is then the read solid's, so a later full rebuild can mark it as built differently, and once saved its solid is saved as built. A step that names edges or faces by the solid's numbering (a fillet, a chamfer, a shell) waits for the rebuilt step, because an STEP round trip moves the solid: Telo test read back 14893.28 mm³ for a step built at 14893.51, and a hole on the read solid came out at 14410.32 mm³ where the same hole on the rebuilt step gives 14893.57. Such an Apply says "Rebuilding the steps…", shows the step as rebuilt, then applies, and a fillet or chamfer asks for its edges again, since the read solid numbers them its own way. If the step no longer rebuilds, nothing is built and the view goes to the last step that does. The solids and kernel answers kept from the read solid are dropped then, and a read solid still on screen is replaced before any edit. A tree whose plate step is the root, or whose file has no `brep` (the engine could not write the plate's step), opens whole at once, counted when it is long. After an engine restart, a tree still on its read step opens from that STEP again, and a tree opened whole opens whole again with its saved solid as the seed.

After a reopen no Prepare step from before the save exists, so Delete branch keeps the root, the branch with the plate's step or the shown step, and a split whose piece is on the plate. A tree the file cannot read (a missing parent, an unknown op, a plate step not in it, a damaged or missing root STEP) is left out: the part opens from its mesh and `brep`, and one notice names it.

## History panel

The open solid's tree is a panel at the bottom left of the Model canvas, under the open tool and above the size chip and the readout (`src/ui/model-history.ts`). The four share one column, so a long warning in the chip or the readout pushes the panel up rather than run under it; on a short canvas the panel gives way first and scrolls, and while a tool is open it keeps to half the column. A long root file name ellipsizes, with the whole name in the tip. At phone width the chip and the readout sit under the toolbar, in the left half so they stay clear of the dock, and the sheet fills the bottom up to them, shrinking and scrolling rather than covering them. `src/model-history.ts` is its layout as data: one row per node, oldest first, drawn as a git graph. The shown step's path runs down the main rail; a fork lists its side branches right under it, each in a column of its own. A join is a merge: its tool's steps come in on a lane of their own ("A tool's steps in History"). The shown step has a filled dot and a bold label, the steps Redo would walk are dimmed, a broken step has a warning icon with its message on hover or focus, and the root is the file name. While the view shows a step other than the one the plate holds, the plate's row has a "Plate" chip.

- **Position** is a fixed row under the header, above the root and apart from the tree; collapsing folds the tree only, so it shows even then. On a short canvas History keeps room for its header, this row and one row of the tree, and with a tool open it may take half the column plus this row. It shows the open object's pose in model space as Place's fields read it, X, Y and Z from where its file put it and the turns, each only when it is not 0 at the panel's precision ("X 10 · Turn Z 30°"), or "At file position". A click opens Place. Reset, shown while the pose is not exactly the identity (so a pose a hair off still reads "At file position" beside it), opens Place, which closes another tool or an edited step whose checked numbers were for the old pose, and puts the part back where its file put it as one Place step: while Place is open Undo takes it back, and it is a Prepare step folded into the visit like a Place gesture, so Prepare undo takes it back too. The row is not a node: no jump, rename, menu, Delete branch or Edit step; it is a group of two buttons outside the `tree`, so the tree's keys never reach it and Tab does. Its text is formatted from the pose the plate object holds and the solid's own box, read once per solid, and only that text changes while Place drags, so the rows are never rebuilt for it. It asks the engine nothing.
- **Labels** come from the op with the panel's number format: "Cut box 10×10×10", "Fuse torus ⌀16 tube ⌀4", "Cut hexagon 5.5 across flats h 2.4", "Hole ⌀5 depth 8", "Hole ⌀3.4 through, counterbore ⌀6.5 × 3.4", "Fillet 3 edges r 1", "Split at Z 42", "Split at Z 42, tilt 15° / 0°", "Scale 200 %", in the part's own frame ("Model space"). A group is one row, named by its `label` ("Pocket 10 × 10, 2 bars"), not one row per step. A row's tip has its whole label, since a long one ellipsizes. A renamed step (double-click the label, or F2) shows its name, and the op is in the tip after it. The name is saved with the project.
- **Folded composites.** A composite the MCP applies now is one group, one history row, named by its label ("front windows", "Ribs × 4"). Files that still have one step per piece, named `prefix k/n` ("rim leaves 3/12", "texture 1/40" through "texture 40/40"), fold those runs: consecutive steps on one chain whose names run `1/n` … `n/n` become one row, "rim leaves · 12 steps", with a chevron. It starts folded. Expanding it shows the steps; collapsing, or Left on the first of them, folds them again. Right on the folded row expands it. A click or Enter on the folded row shows its last step. The view stays on a step: the folded row is marked current while the shown step is one of the run, and the tip names that step. Undo from the last step of the run jumps to the step before the first, and Redo from there jumps back to the last. A gap in the numbers, a side branch, or a tool lane between the steps leaves them as separate rows, and Undo moves one step. A group beside such a run is its own row, and Undo of the group moves one step. The header's count stays the number of steps.
- **Built by a recipe.** When the open object has `mcpModel.recipes[id]`, the History header shows "Built by a recipe", then the recipe's name and parameters ("pegs · count = 3"). The line is read-only. Changing the parameters and rebuilding the part comes later. Opening a project keeps `mcpModel`, and saving writes it back, so the recipe is still there next time. A step an MCP composite renamed is saved as that step's name, so the folded rows are there after the file opens.
- **Moving.** A click or Enter shows that step. While Pattern or Mirror is open, Ctrl-click (Cmd-click) adds or removes that row from the steps to repeat and does not show it ("Pattern and mirror"). Up, Down, Home, and End move and show the step after a 200 ms pause (`JUMP_WAIT_MS`), so a run of presses asks the engine for the last one only. Left and Right switch to the next branch at the nearest fork, at the same depth or that branch's last step. A newer jump wins over one still on its way: the late reply is kept in the client's recent solids and not shown. A step already on its way is not asked for again. While a jump is on its way, Apply, Undo, Redo, and STEP are off. A press still in its pause when Model closes does nothing.
- **Rows do not move under the pointer or the keys.** While the pointer is over the panel or focus is in it, each fork keeps the branch it followed; when both leave, the shown step's path moves onto the main rail.
- **Delete branch** (the row's menu, or Delete) drops the step and everything under it, here and with the engine's `drop`. It is refused, with the reason in the menu and the readout (in the sheet at phone width), for the root, a branch that holds the shown step or the plate's step, a branch with a step the plate held before (a Prepare undo can put its mesh back), and a branch whose split made a part of its own. There is no undo for it, so it asks for no confirmation. Model never closes a tree because the plate's mesh is not in it: a Prepare undo or redo can bring one of its meshes back.
- **Edit step** (the row's menu, the pencil on the row, or Shift+E) opens the step's tool with its numbers ("Editable history").
- **Keys.** Shift+H goes into the panel from anywhere in Model, opening it if needed, and back out; Esc leaves it. Shift+F10 or the menu key opens a row's menu. The list is a `tree` with `treeitem` rows (`aria-level` is the branch depth, a fork has `aria-expanded`, the shown step is `aria-selected`) and one row in the tab order. Branches never fold away, so a fork stays expanded, and Left and Right switch branches instead of folding them. The tree is `aria-busy` while an arrow press waits out its pause. Leaving the panel puts focus back where Shift+H came from, else on the canvas.
- **The count** in the header ("History · 7") is the rows the tree draws: the part's steps on every branch, its root included, and each join's tool steps on their lanes, nested lanes too (`rowCount`). So the header and the list it folds always agree, and the number stays one number: a split such as "3 + 2 tool" would make the header longer than the panel's narrowest width, for a difference the lane's hollow dots already show. The count is the header button's name too, which a screen reader reads with the panel's "History" and the tree's "Model history"; neither of those carries a number. It is worked out only when the tree, a tree its joins reach, or the row on screen changes.
- **Collapsed** to its header it stays collapsed for that browser (`localStorage`). At phone width it is a sheet over the canvas, opened from the History button in the Model toolbar.
- **Cost.** Rows are patched by node id when the tree value changes, and not built at all while the panel is collapsed, the sheet is closed, or Model is hidden. Drawing asks the engine nothing.
- **View** (`src/ui/model-look.ts`, the foot beside Reset view) is how the solid is drawn. It does not change the probe or the solid. **Section** is a plane on X, Y, Z, or a picked flat face, slid by the Offset field or by the one arrow on the plane. The side the normal points toward is hidden, and the cut is drawn in the inside colour. Flip swaps that side and leaves the plane where Offset put it. A curved face is refused ("Pick a flat face. This one is curved."). **Colour by step** gives each history row a swatch and paints each face in the colour of the node in `stepFaces` that made it. Hovering or focusing a row tints that step's faces either way. A seeded tip, whose saved solid has no per-face history, owns every face it holds until a replay builds them again.

## Editable history

A step's numbers can change after it was applied; the owner asked for it on 2026-10-15. An edit never rewrites a step, since node ids are named by the plate's step, by split pieces, by kept joins, by Prepare undo and by saved files. It forks, as a new edit from an older step always has: the edited op is a new sibling of the step, the steps below replay under it as new steps, and the old branch stays as it was, for Delete branch to remove (`src/model-edit.ts`).

- **Opening.** Edit step in a row's menu, the pencil a row shows on hover or focus, or Shift+E: the focused row while focus is in History, else the shown step (and nothing while an edit is open, since the step shown then is the parent). Double-click stays rename. The step's tool opens with the numbers it was applied with, taken back into model space at the object's pose (`fromSolidOp`, the inverse of `toSolidOp`), under a header such as "Editing step 3: Hole ⌀5 depth 8". The view shows the step's parent, with the tool's ghost and handles, as when the step was first applied, and the dry-run runs on the parent. Apply reads Update, and stays off while the panel still says the step as it is ("Change a number to update this step."), so an untouched panel asks the engine nothing. A field left alone sends its stored number exactly, though it shows it to the hundredth. Cancel, Esc, or another tool puts the view back where it was; a click on a step in History goes there instead. While a step is edited, Undo and Redo are off, and Delete branch keeps the branch with the step edited or the step Cancel goes back to. A save while a step is edited saves the step shown before the edit as the shown one. A tree from a project still on its STEP-read step opens whole first, as for an Apply.
- **What changes.** A boolean: its op, its primitive, sizes, origin and turn, but not Object. A hole: origin, radius, depth, Through all, the counterbore's box and numbers, and its drill direction, kept until a face is picked. A split: shown on the model axis its normal is nearest, with the tilts from it and the plane's position on the line through the part's middle; a normal pointing down that axis keeps its side. A fillet or chamfer: its size and its edges, picked again for the panel by midpoint and length on the parent (the readout says how many are no longer there). A scale: its factor. A join: Fuse, Cut or Common, and Keep the tool object; its tool object and step stay as applied, and to change them the step is deleted and joined again. The tool's own steps are edited from their rows in the join's lane ("A tool's steps in History"). Update of a join with Keep off takes its tool off the plate if it is there, as Apply does; Keep turned on does not bring a tool back that an earlier Apply took off, which Prepare undo does. A new solid's root edits in New solid's panel and becomes a `root` step right under the root, so node 0 never changes. A solid that started from a sketch keeps its pencil; Edit step says "This solid started from a sketch. Open the sketch to change it." The sketch editor is not in this change, so the panel does not open. An opened STEP is a file, and a split piece's root is its split's: neither is edited (Edit step says why, and the row shows no pencil); nor is a step under a broken one. A pocket, boss, texture, array, ribs, or text group reopens that tool from its source and expands again on the parent.
- **Which steps replay.** The shown branch below the step: the path down to the step shown when that is below it, then on to the branch's tip; else the branch from the step. A branch goes on as History draws it, with the child Redo follows, else the newest, so a reopened tree, which knows only the path to its shown step, replays its other branches whole. A `root` step on the way is left out, since the edit's new root stands in for it. A step Redo would walk is part of the branch the user sees, so it comes along rather than stay behind. User names come along too.
- **Update** is one `edit` call. While it runs the readout says "Rebuilding 4 steps…"; the UI is not held, and Cancel goes back at once, to a step kept among the recent solids when the edit opened: what the engine built for it is dropped when its answer lands. The view goes to the last step that built, and Redo stops there. Numbers that already built a branch from the same step, with the same steps after it, show that branch instead of building it again.
- **A step that no longer builds** (a fillet whose edge is not on the new solid, a hole that misses) stops the replay. It is kept, broken, with the engine's message on its row and the steps after it under it, and the readout names it: "Step 4, “Fillet 1 edge r 1”, could not be rebuilt: That edge is not on this solid." It can be edited, which forks it in turn and replays what is under it, or its branch deleted. Nothing is skipped and no solid is guessed.
- **Undo** from the edit's tip goes back to the step shown before the edit, on the old branch, and Redo forward again; past that, Undo and Redo walk the tree as ever.
- **Split pieces.** A replayed or edited split builds its own side only and makes no new piece: a piece already on the plate is a part in its own right and stays as the older split cut it, which the readout says ("telo split stays as the older split cut it."), and so does Model each time it opens that piece while its part's plate step is not under the split that cut it. Re-rooting the piece on the new other half would replace a part behind the user's back.
- **Joins.** A join in another part that names a step of the edited branch keeps naming it, untouched; the readout says so.
- **Plate.** The plate takes the new tip by the lazy commit, in the visit's one Prepare step, and Prepare undo puts the old mesh back. A commit while a step is edited takes the step shown before the edit.
- **Saved.** Nothing new beyond the nodes and the shown step: a fork reopens with both branches, and a `root` step is saved as its op. An app from before this reads `root` as an unknown op and leaves that tree out, opening the part from its mesh.
- **Cost.** The parent's kept solid is the start, a kept probe of the edited op is reused, no replayed step but the last that built is tessellated, and the panel's numbers are worked out once, when it opens.

## A tool's steps in History

A join used to show as one row, and its tool usually leaves the plate, so the tool's steps could be neither seen nor edited. The owner asked on 2026-10-16 not to lose them, and approved both parts below, as Fusion and Onshape keep a combine's tool body with its features and recompute the result when one changes (`src/model-history.ts`, `src/model-edit.ts`).

- **The lane.** Right above each join, the tool's steps from its root to the step the join takes come in on a column of their own and merge into the join's row, as a merged branch does in git. The lane shows that path only, the history that made the tool as the join took it; the tool's other branches, and its steps after that one, belong to the tool object's own History. Every join has its lane, on any branch: on the shown step's history it is lit as the rest of that history, elsewhere it is dim. A tool's dots are hollow, and the lane's first row carries the tool's name (unless that row's label is the name already). A tool whose own history has joins nests their lanes in its lane, to any depth; the cycle refusal per tree ("Booleans between objects") keeps the nesting finite. A tool tree the app does not have draws no lane.
- **A click on a tool's row** (or Enter, or an arrow after its pause) shows the tool as it was at that step, read-only: its solid where the join put it (the open object's pose, then each join's `relative` in turn, `toolPose`), with the open solid grey behind it as it was on screen, the tool's own plate object, if Keep left one, hidden so it does not stand in the way, and the other objects grey. Nothing else moves: the open solid's shown step and plate step, its Redo, and the tool's own tree (its shown step, plate step and Redo) stay as they were, and the Plate chip marks the step the plate holds. The tools wait, each tip saying why, and picks are off; New solid stays. A click on one of the part's own steps, or Esc on the canvas, goes back to the part; Undo and Redo step the part's own history as ever, from the step the part shows, and so leave the tool's step too. Deleting the branch of the join whose tool is looked at goes back to the part. The step's solid is asked of the tool's tree once (`goto`) and kept among the recent solids.
- **What a tool's row allows.** Edit step, from the pencil, the menu or Shift+E, as below. Rename renames that step in the tool's tree: it is the same step the tool object's own History shows, so it reads the same in both, and no plate changes. Delete branch is off, with the reason in the menu: every row of the lane is on the way to the step the join takes, which the engine keeps while the join names it; deleting the join's branch is the way.
- **Edit step** opens the step's tool on its parent in the tool's tree, shown where the join put the tool, with the step's numbers in model space at that pose, under "Editing Rod 1, step 1: Scale 150 %" (or "Editing Rod 1's primitive: …" for a New solid tool's root, or "Editing Rod 1's sketch: …" for a sketch-started tool's root). The dry-run runs on that parent, in the tool's tree. Update is one `edit` call with `tools` (`crossEdit`, `crossEditRequest`): the tool's tree forks at the step, the edited op a sibling of it, and replays down to the step the join takes; each join above is built again on the new tip, as a sibling of itself, its tree replaying down to the step the next join takes; and the open solid's steps after its join replay as Edit step replays them. The old branches stay in every tree, for Delete branch. The view goes to the open solid's new tip, and Undo goes back to the step shown before the edit, as for any edit. Numbers that built these branches before show them instead. When only some trees still have theirs, as after Delete branch took the part's, the edit takes the branches still there, deepest first, and builds only the trees above them: the first join without its branch is built on the tip below it, which the engine's `edit` takes as any join's tool step (`crossPlan`). So each identical edit lands on one branch in every tree, nothing is built twice, and a failure takes back only what this edit built. A branch counts only while it is whole and none of its steps is broken: every sibling with the same numbers is searched, so one cut short by Delete branch in the tool's own History is passed over for a whole one beside it, and a branch kept broken is built again, as a retry. The tool's tree takes the new branch without moving its shown step, its plate step, or which child its Redo follows from the step edited, so the tool object's own History keeps its shape.
- **One call, not two.** Two calls composed by the client would leave the tool's new branch behind whenever the second failed, or the app or the engine stopped between them, and that branch would then need a cleanup that can fail too. One call under the engine's lock keeps a failure clean: when the edited step, or a join whose tool built, does not build, nothing is kept in any tree and the readout says why, as for an edit of the part's own step. A tool step that no longer builds is a broken replay like any other: it is kept broken, the join it fed is kept broken too ("The tool object's step could not be rebuilt: …") with the part's later steps unbuilt under it, the view shows the join's parent, and the readout names the tool's step: "Step 2 of Rod 1, “Hole ⌀4 depth 12”, could not be rebuilt: …". That step can be edited from its row in turn.
- **The tool object on the plate** (Keep ticked, or brought back by Prepare undo) keeps its own plate step: a fork in its tree moves neither its plate nor its shown step. The readout says so: "Rod 1 on the plate keeps its own steps; only this part's join takes the edit."
- **Saved.** Nothing new in the file: the tool's tree is saved with its new branch, in `modelTools` or with its object, and the join names the new step. A reopened project draws the lanes and opens a tool's tree when one of its rows is first shown or edited, the whole tree first for a tree still on its STEP-read step. An app from before this reads the file as before.
- **Keys and ARIA.** A tool's rows are `treeitem`s one level below their join, which owns them (`aria-owns`) and is `aria-expanded`, so a screen reader hears them as the join's children though they are drawn above it; each reads as "Rod 1: Scale 150 %". Up and Down walk every row in order, a tool's included. Right on a join goes into its lane, to the step it takes, and Left on a tool's row comes back to its join, as a tree item's children are reached; so on a join, Right no longer switches to a branch on its right, which Left and Right still do everywhere else. Rows are named by their step and the joins they are reached through (`RowKey`, "2/1": step 1 of the tool the join at step 2 takes).
- **Cost.** The lanes are laid out with the rows, only when the open tree, a tree its joins reach, or the row on screen changes: never per frame, per hover or per Place drag. Nothing is asked of the engine for a row until it is clicked or edited.

## Viewport handles

Every Model tool is both typed and dragged. Each number in the open tool's panel has a handle in the viewport, drawn in Prepare's gizmo style, and a drag writes the field as if it were typed. The ghost, the dry-run, and Apply follow, and a typed number moves the handle. Shift slows the pointer to a tenth for fine control, and Ctrl (Cmd on a Mac) snaps to the handle's step: 1 mm, 0.5 mm for a blend or hole radius, 0.1 for a scale factor, and 15° for a turn. A label by the pointer shows the value. The panel's scrub labels use the same keys.

## In-canvas interaction

Sketches, push/pull, and the idle edge drag share helpers in `src/interact/`. Push/Pull calls the heads-up box, the one-axis drag, and the face prism. The dock above is unchanged: Place and Workplane still use it, and Fillet (L) and Chamfer (Shift+L) still open their panels. The helpers are an arrow on a face, a box of sizes at the pointer, and a mesh drawn on the client while the pointer moves:

- **Heads-up sizes** (`hud.ts`). A small box at the pointer shows one, two or three live sizes, such as "12.5 mm · 30°". Typing a number, or an expression with the same evaluator the MCP uses (`evaluate` in `mcp/expr.ts`), edits the active size. While that size is focused it shows the expression; otherwise it shows the number, with a small ƒ when the text was an expression. Tab and Shift+Tab move between the sizes, Enter sets them, and Esc cancels. The box is an `aria-live` region. It flips to stay on the canvas, and it does not cover the pointer when the canvas has room. A name that is not a parameter is refused in a sentence: add it in Parameters, or type a number.
- **Snapping** (`snap.ts`). A point on the sketch plane snaps within 8 px, in this order, and a later kind never wins just by being closer: sketch endpoints, midpoints, centres and intersections; then a projected solid's vertices and edge midpoints; then a point on a sketch curve, then on a projected edge; then a horizontal or vertical line from the last point, a line parallel or perpendicular to the last segment, or the line of a projected edge; then the grid. The grid steps by 1, 2 or 5 times a power of ten, and it never draws closer than 12 px.
- **One-axis drag** (`drag-axis.ts`). The pointer's ray meets the drag line the way a dock arrow does (`lineParam`). A double-click on the same spot repeats the previous distance. Ctrl snaps to whole steps and ignores face heights. Without Ctrl, a face height within 8 px wins, and the result carries the face so the view can draw a dotted line to it. Shift keeps hundredths, as a dock drag does.
- **In-place arrow** (`in-place-arrow.ts`). One arrow, seated on the face or region at the pointer, pointing along the outward normal. It is a feature handle, so the view draws it with the other feature handles and not on the dock. The shaft starts 0.125 handle-units off the face, along that normal, so it does not run into the solid. The view already draws handles with no depth test, so the arrow stays visible. Place and Workplane keep the dock.
- **Ghosts** (`ghosts.ts`). While the pointer moves, only a client mesh is drawn. A face becomes a prism: its triangles moved along the normal, with a wall on each boundary edge. A sketch region is ear-clipped, holes included, and extruded the same way. A revolve is a lathe of the outline in 48 steps. A fillet is a tube of the blend radius along the edge, open at the ends, as the blend ghost in the view is. The kernel is not asked until the pointer has been still for 300 ms, the same `PROBE_WAIT_MS` as a typed number.
- **Edge drag** (`src/interact/edge-drag.ts`, wired in `src/app/edge-drag.ts`). With no other model tool open, hovering an edge lights it and seats a knob on its midpoint. The knob points into the angle between the edge's two faces: the bisector of their outward normals, read from the mesh. Drag the knob to set a fillet radius. Hold Alt for a chamfer. If that edge is already selected, every selected edge is blended. While the pointer moves, only the blend ghost is drawn. After the pointer has been still for 300 ms the kernel probe runs, and its preview replaces the ghost. If the probe names a largest size, the drag stops there and the readout says "The largest that fits is N mm." Releasing the pointer applies the step (one undo). The readout then says "Fillet 2 mm · Tab to edit". Tab within 3 seconds reopens the size box on that step; Enter sets the new size and Esc cancels. Typing a number while the pointer is on an edge opens the same box. The box is the HUD above. P is Push/Pull, and Split's key is D. There is no separate toolbar button for this drag.

`src/interact/interact.test.ts` checks the snap order, the drag mapping, and the ghost volumes. `src/interact/edge-drag.test.ts` checks the bisector, which edges move together, the clamp, and the readout sentences.

### Sketch

Sketch (S in Model) draws on a plane. Line and Rectangle sit on the sketch card; the other drawing tools are in its Draw menu. S in Prepare is still Scale. The button has no `data-tool`: it is not a dock-handle tool, and it does not join the drag checklist. It is an icon, and icon buttons use 1 px of padding, so the bar still fits at 1440 px with a pick's chip. It stays visible on an empty plate, next to New solid.

Click Sketch, then a flat face, one of the three origin planes at the part origin, or the workplane. The card under the toolbar has the same planes, so the choice does not depend on a ray. Double-click a flat face to start there when Push/Pull is not the gesture under the pointer. In Face mode, double-click still repeats the last push or pull. On an empty plate the card's Sketch on the bed starts on XY at Z = 0.

The camera turns onto the plane in 250 ms and then stays on the normal. Middle-drag pans, the wheel zooms along the normal, and right-drag rolls about the normal. Look around (O) gives the left button back to orbit; O again locks the view for drawing. The solid is dimmed. Edges that lie in the plane, the face outline, and edges that cross the plane are faint reference lines. They snap. They are not sketch entities until Use copies the one that was clicked.

The grid is 1, 2 or 5 times a power of ten, never closer than 12 px. Entities are fat lines, lifted 2 px toward the camera. Points are screen-size dots.

Line (L): click each point. Double-click or Esc ends the chain. Click the start point to close it. The heads-up box shows length and angle. Rectangle (R): two corners. Ctrl on the first corner draws from the centre. The box shows width and height. Tab moves between the sizes, Enter sets them, Esc cancels the size. Both tools also take the mouse.

The other drawing tools are in the sketch card's Draw menu, not on the Model toolbar, so the bar still fits at 1440 px. Each one also has a key while the sketch is open, and each size can be typed or dragged:

- **Circle (C).** Click the centre, then a point on the radius. The box shows the diameter.
- **Arc (A).** Click the start, the end, and a point on the arc. The box shows the radius and the sweep. Shift+A, or Shift on the click, draws the arc tangent to the last line, from that line's end.
- **Polygon (N).** Click the centre, then a corner. The box shows across corners, across flats, and the number of sides, starting at 6.
- **Slot (Shift+S).** Click the first centre, the second centre, then the width. The box shows the length and the width. The outline is two lines and two semicircle caps.
- **Spline (B).** Click through the points. Double-click, Enter, or Esc ends it. Click the start point to close it. There is no size to type.
- **Trim (T).** Click the piece to remove, between the nearest crossings. Enter trims the piece under the pointer.
- **Offset (F).** Click a line or a connected chain and drag, or type a distance. Positive is to the left of the chain. The original stays.
- **Fillet corner (G).** Click two lines that meet and drag the radius, or type it. The lines shorten and an arc fills the corner.
- **Construction (X).** Click a line to toggle it, or press X with a selection. A construction line still snaps and still cuts a trim, and it is not part of a region.
- **Use (U).** Click a faint reference edge to copy that edge into the sketch, or click the face outline to copy the whole outline. A second use of the same edge says it is already there.

Click selects. A box dragged left to right keeps what it encloses; right to left also keeps what it crosses. Drag a point or a line to move it. A corner shared by two lines moves both. Delete removes the selection.

Ctrl+Z and Ctrl+Y (and Ctrl+Shift+Z) undo inside the open sketch, and the History buttons do too. They do not step the solid's history until the sketch is closed. Esc ends the current gesture; Esc again finishes. Finish keeps the sketch as a card until it is discarded. A sketch with nothing in it is dropped. A sketch with no feature is not saved, and reopening the card starts a fresh undo stack.

Constraints and driving dimensions are in the sketch card's Constrain menu (Geometry, Size, Edit), not on the Model toolbar, so the bar still fits at 1440 px. The solver is in-house: a damped Gauss-Newton (Levenberg-Marquardt) over point coordinates, circle radii, and arc sagitta in `src/sketch/solve.ts`. PlaneGCS and any other LGPL or WASM solver are not used. The decision is (a) in `docs/plan-gui-cad-modeling.md` §4.5, recorded here on 2026-10-19: tens of entities, no extra licence. A sketch with no constraint is not solved, and a drag of it moves the points exactly as before. Coincident is a shared point (the two ids become one); removing the constraint does not split them again, and undo restores both points. Horizontal, vertical, parallel, perpendicular, tangent, equal, concentric, fixed, and midpoint are geometric. Distance, length, radius, diameter, and angle are driving dimensions, stored in the optional `dims` field. An older file with no `dims`, and an unknown dimension record, opens unchanged and does not start the solver.

A driving dimension is a label on the sketch. Click it and type a number or an expression; Enter sets it and Esc leaves it. The same text can be typed in the heads-up box. The app installs `setDrivingEvaluator` in `src/sketch/constrain.ts` with the project's parameters, so a label accepts `wallH / 2` and keeps that text on the dimension. A label that is an expression shows the number and a small ƒ; the field shows the expression while it is focused. A name that is not a parameter says to add it in Parameters, or type a number. Labels are accent-coloured while the sketch still has freedom, and they turn the ok colour when it is fully defined. A constraint that repeats another is reported as redundant. One that cannot be met is reported as conflicting, and the geometry stays as it was. Dragging a point re-solves. A fully defined sketch does not move. Undo and redo cover constraints and dimensions. Delete on a selected dimension removes that dimension.

Extrude (E, or the card's Extrude button; there is no toolbar button and no global E, because Prepare already uses E) takes the selected regions, or the region under the pointer, or the only region. The arrow sits at the region's centre along the plane normal. Drag sets a signed distance and the ghost follows; after the pointer has been still for 300 ms a kernel preview runs, except for a new object, which stays a ghost. Typing the distance does the same, and Tab on the last field adds the other side (equal sides are symmetric) and then a draft. M, or the card, cycles New object, Join, Cut, and Intersect. With nothing chosen, a new solid is always a new object; a sketch on a face that is pushed in is a cut, and one pulled out is a join. Enter, Apply, or a click that did not drag keeps it. Esc leaves the extrude and stays in the sketch. The canvas carries `data-extrude` (`off`, `aim`, or `drag`), `data-extrude-mode`, `data-extrude-depth`, and `data-extrude-regions`. Apply stores the extrude, with a copy of the sketch on it, and pins the sketch card. History Edit on that step, or on an extrude that is the solid's root, opens the same sketch and drag with the old distance.

Revolve (V, or the card's Revolve button; there is no toolbar button, and V is not taken outside a sketch because the preview uses V to cycle the view) takes the same regions. The axis is the sketch line, construction line, or projected solid edge under the pointer, or the plane's U or V axis, drawn dashed while it is being chosen. A sketch line wins over a construction line, then a projected edge, then U or V, and the nearer one wins a tie. Nothing under the pointer uses V. The first click locks that axis. The ring sits at the region's centre. Dragging it sets the angle, one pixel across the axis is one degree, Ctrl snaps to 15°, and the angle stays between 0.1° and 360°. The field opens at 360, and typing 360 snaps to a full turn. A region that crosses the axis is drawn red and Apply does not send it ("The profile crosses the revolve axis. Keep it on one side."). Join, cut, and a new object follow the extrude's rule, with a positive distance so a sketch that touches the solid joins unless M says otherwise. Enter, Apply, or a click after the axis is locked keeps it. Esc returns to the sketch. The canvas carries `data-revolve` (`off`, `aim`, or `drag`), `data-revolve-mode`, `data-revolve-angle`, `data-revolve-axis` (`u`, `v`, `line`, `construction`, or `edge`), `data-revolve-regions`, and `data-revolve-cross` (`0` or `1`). Apply stores the revolve with `loops`, `axisOrigin`, `axisDir`, `angleDeg`, and a copy of the sketch. History Edit reopens that sketch and the ring with the stored angle.

Loft (Shift+L, or the card's Loft button; there is no toolbar button) takes sections in the order they are picked, two or more. The regions of the open sketch start the list. A click on a pinned sketch card adds that sketch's region, or drops it when it is already a section. A click on the open sketch does the same for the region under the pointer. A click on a flat face of the solid, nearer than the sketch plane, reads that face with `faceLoops` and adds it as a section (`origin`, `turn`, `loops`). R, or the card's Ruled button, sets `ruled`. Sections that lie in one plane are refused ("The loft has no volume: its sections lie in one plane."). Join, cut, and a new object follow the extrude's rule, with a positive distance, so a sketch that touches the solid joins unless M says otherwise. Enter or Apply keeps it. Esc returns to the sketch. The canvas carries `data-loft` (`off` or `pick`), `data-loft-mode`, `data-loft-sections`, and `data-loft-ruled` (`0` or `1`). An older loft with no `drawing` still opens, and Edit rebuilds a sketch from each section.

## STEP save

Model mode writes the open solid as AP214 IS, a manifold solid B-rep, through `STEPControl_Writer`, only for the STEP button (the shown node) and the MCP server's `model_export_step`. The STEP button downloads that file and keeps nothing.

## Saved solid

The plate object keeps its step's solid as optional `brep`, in the same shape as `mesh`: name (`part.brep`), base64, length, and hash. Since `.lime` version 3 it holds the solid as `export` writes it in `brep`: a header line `LIMEBREP 1 <Open CASCADE version> <volume> <edges the step made>`, then the shape in Open CASCADE's binary format (`BinTools`, format 4, without triangulation). BinTools is in `TKBRep`, which the app already ships, so the bundle gains nothing. An edit does not write it. The solid of the node each plate object holds is written when it is needed: leaving Model (in the background), a project save, and Duplicate (a copy's tree is rooted in it). A written solid goes to every plate object and Prepare step whose mesh token (`meshTokenOf`) is that node's mesh, so a step captured before the write gets it too, and to the node, so the plate gets it back when it returns there. Prepare steps share each buffer rather than copy it. A solid the engine can no longer write loses its `brep` at save rather than keep one from an older shape. Prepare history folds a Model visit that changed the plate into one step on leaving Model; the tree keeps the steps in between.

**Why the binary format.** The owner asked on 2026-10-17 for a reopened part to show in seconds; reading the back cover's 18 MB STEP took 25 s of the 28 s Model took to show it. The binary format is every number as the kernel holds it, with sub-shapes in the order it numbers them, so a read is the step exactly: the same fingerprint, the same face and edge numbers, the same volume (kept in the header, so a read integrates nothing), and the edges the step made (for a blend that picks a step's edges). A STEP read is not: the back cover's plate step read back with 11964 edges where its history builds 11965, which is why a file before version 3 could not build a fillet on its read step. The owner allowed breaking older apps (2026-10-17), so a file keeps no STEP for them: STEP is written only for export.

| Back cover (4707 faces, 326 steps) | Before (STEP) | Binary |
| --- | --- | --- |
| `brep` in the file | 18.1 MB (24.1 MB base64) | 3.5 MB |
| `.lime` | 27.2 MB | 7.8 MB |
| Engine read | 13 to 25 s | 0.05 s |
| Model shows the solid (web UI, real engine) | 25.6 to 28.3 s | 1.4 s |
| First edit done after that | 8.6 to 9.2 s | 5.4 s |
| MCP `project_open` | 264.5 s (whole history rebuilt) | 1.15 s |

A Boolean on the 4707-face solid was then 1.8 to 2.4 s of Open CASCADE's boolean itself, of a 2.3 to 2.5 s check. Most of it was waste, found on 2026-10-18: the two-shape `BRepAlgoAPI_Fuse`, `_Cut` and `_Common` constructors build at once, so every boolean was built twice, the first time destructively; `BRepMesh_IncrementalMesh` meshes in its constructor, so a second `Perform` checked every face again; the volume was integrated on one thread; a step meshed every face; and the Model view drew every frame while it was open, which in a browser drawing without a graphics card took the processor the engine needed. Now a check on the back cover is 0.41 to 0.54 s in the engine (the boolean 0.33 to 0.50 s of it) and 0.6 to 0.8 s from the last number to the shape on screen; an Apply that takes it is 0.25 to 0.3 s.

A boolean that worked only on the faces near the tool would be faster again, but Open CASCADE numbers a boolean's result as it rebuilds the whole shell, and fillets and the MCP server name edges by those numbers, so a local result numbered any other way would move the edges of every saved step after it. The boolean stays whole. Triangulation is not stored: meshing the read solid is 0.7 s, and a stored mesh would roughly double the bytes to save some of that.

**Compatibility.** `.lime` is version 3 when it is a plate (`PROJECT_VERSION`); a one-object file without per-object fields stays version 1. `migrations[2]` takes a version 2 file as it is: its `brep` is STEP, which the engine reads too, and Model opens it as before ("Saved with the project"). The app writes the binary solid at the first save after the step was rebuilt, or after a new step; until then a version 3 file can still carry that STEP `brep`, and the code tells the two apart by their first bytes (`isBrep`), never by the file's version. The MCP server writes it at its next commit or `project_save` (its trees are always whole), not in an autosave, which commits nothing. An app before version 3 refuses a version 3 file ("This project is version 3…"). A binary solid another Open CASCADE wrote is read when BinTools can read it, which covers every older format; the header names the version, and a failed read says it. A root opened from a step's saved solid (a Duplicate's copy) made every edge it has, as any root did, whatever edges the step made. Root names stay labels: a root read from a saved solid keeps the `.step` name History shows. A seed is refused when it does not read, is STEP, or does not match its step's saved fingerprint (a step saved without one, as the MCP server saves its steps, takes its own saved solid unchecked); the volume compared is the one its header carries, so the check is of the faces, the edges and the header, and the bytes themselves are guarded by the record's hash. A refused seed costs a replay of the history, the only fallback left without a STEP in the file, so nothing else is kept for it. A damaged `brep` fails the open, as before.

Opening Model reloads `brep` when the object has one, so an edited solid is not stuck as a mesh. The STL is what the slicer reads. Opening Model still does not replace `sourcePos`.

## What this change is not

- No change to `tools/golden_ab.sh`, toolpath planning, or STL/3MF geometry.
- The slicer core does not link Open CASCADE. Since 2.6.1, desktop, CLI/HTTP, and MCP install a host STEP mesher at startup when `lime-model-load` can load the OCCT bridge. Preview and slicing use the same loader. Without OCCT (including a stub build), truck remains the fallback, with known closed-spline and trim limitations. Once OCCT is selected, import failures are returned; they do not silently retry through truck.

### STEP import for slicing (2.6.1)

`lime-model-load::step_mesher` supplies a function returning triangle positions in millimetres in the file frame, plus the bridge binary's SHA-256 identity. The host installs it once with `lime_slice_core::set_step_mesher`, before any imports or jobs. The core validates the chord tolerance, uses the supplied triangles, and retains its existing seating and pose rules. Its default truck implementation is unchanged. The disk slice cache includes the mesher identity so a truck result cannot answer an OCCT request, or survive a bridge rebuild.

The bridge's `capabilities` call returns `{stepMeshing: true}` when its STEP reader is linked. `meshStep` accepts `{call: "meshStep", dataB64, chordMm}` and returns the existing `lime-solid-2` mesh reply. It reads and meshes a temporary shape under the kernel lock, then releases it without creating or evicting history documents. `positions` contains nine f32 coordinates per triangle; `triangles` contains face IDs, not vertex indices. The loader rejects surfaces without solids, empty meshes, and non-finite coordinates. An older loaded bridge must be upgraded alongside the host; an unsupported call is an error, not a truck fallback.

OCCT handles units and placements. For legacy assemblies with bare representation relationships and no context-dependent product occurrences, the reader traverses those relationships, using OCCT to transfer leaves and compute transforms. Cycles and mixed geometry/assembly containers are refused instead of losing components.

The regression fixture `crates/lime-slice-core/tests/fixtures/duck-plate.step` is the original 17-face modeler export (about 500 KB), including closed spline wings and trimmed sphere/loft faces. OCCT's reference solid has volume 32645.87 mm³ and area 6100.4 mm². At the default 0.05 mm chord, the test requires both mesh measurements within 0.5%, checks bounds and preview/load agreement, and exercises inch units and assembly instances. Run:

```powershell
$env:OCCT_ROOT = "D:/occt-7.9.2"
cargo build -p lime-model-occt
# Point at a bundle containing the bridge and its OCCT DLLs.
$env:LIME_OCCT_BRIDGE = "<bundle>/lime_model_occt.dll"
$env:LIME_REQUIRE_OCCT = "1"
cargo test -p lime-model-load --test step_import -- --nocapture
cargo test -p lime-slice-core --test step_load --test step_backend --test pipeline_profile
```

`LIME_REQUIRE_OCCT=1` makes a missing bridge fail the regression instead of skipping it. The Windows OCCT CI job runs this check against the bundled bridge.
