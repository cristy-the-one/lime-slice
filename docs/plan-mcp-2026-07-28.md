# Plan: speak MCP 2026-07-28

"MCP 2.0" is the name the SDKs use. The specification revision is **2026-07-28**, final since 28 July 2026, and the
official SDKs that speak it are version 2 (TypeScript: `@modelcontextprotocol/server` and `@modelcontextprotocol/client`).
The changelog at `modelcontextprotocol.io/specification/latest/changelog` shows nothing newer.

The headline change is a **stateless** protocol. There is no `initialize` handshake and no session id. Each request
carries its own protocol version, client info and capabilities in `_meta`, and a new `server/discover` says what a server
speaks. The other changes are listed in §2.

## 1. Where Lime Slice stands

- `mcp/protocol.ts` is a hand-written JSON-RPC handler over **stdio**. It does not use the SDK; the SDK v1
  client is used only in tests (`stdio.test.ts`, `long-call.test.ts`, `native-load.test.ts`, `part-a.test.ts`).
- It speaks `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` and `2026-07-28` (M1). A request whose `_meta`
  `protocolVersion` is unsupported is `-32022` (`UnsupportedProtocolVersion`: `message` "Unsupported protocol version",
  `data.supported`, `data.requested`). The final schema's constant is `UNSUPPORTED_PROTOCOL_VERSION = -32022` at
  [schema/2026-07-28/schema.ts line 450](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/2bbace557bbf2cb5d03d6f9b48905415cd7607b0/schema/2026-07-28/schema.ts#L450)
  (commit `2bbace557bbf2cb5d03d6f9b48905415cd7607b0`). [PR 3092](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3092)
  moved that constant from `-32004` to `-32022`. An unknown resource is `-32602` (`INVALID_PARAMS`, schema.ts line 315);
  the same file's comment at line 423 says `-32002` was replaced by `-32602`. `initialize` answers a version it supports:
  an unknown one gets `2025-11-25`, and `2026-07-28` is echoed. `initialize` with no `protocolVersion` still answers `2024-11-05`.
- Methods: `initialize`, `ping`, `server/discover`, `tools/list`, `tools/call`, `resources/list`, `resources/read`,
  `prompts/list`, `prompts/get`. Notifications sent: `notifications/progress` (on a call's `progressToken`) and
  `notifications/tools/list_changed` (tool groups, older clients only). Received: `notifications/cancelled`.
- Once per process, stderr (never stdout) logs `lime-slice mcp: protocolVersion=… clientInfo=… clientCapabilities=…`
  from `initialize` params, or from the first request `_meta` when the client does not send `initialize`.

- There is no HTTP transport, and no elicitation, sampling, roots or logging.
- State (workspace, open project, plate, undo history, jobs) lives in the server process, one process per client.
- Tool groups: an older client's `tools/list` starts with the discovery tools, and a call into a closed group opens it and sends
  `list_changed`. A 2026 client gets the discovery tools only and no `list_changed` (D1, shipped with M1).
- Long work answers with a job, and the client polls `slice_wait`. A 2026 client whose request lists `io.modelcontextprotocol/tasks` gets a task instead (M3).

Because the transport is stdio and the state lives in the process, the stateless change costs this server little.
There is no session header to drop and no load balancer to share state across.

## 2. What the revision changes, for this server

| Change | SEP | For Lime Slice |
|---|---|---|
| No `initialize`; version, `clientInfo` and capabilities in each request's `_meta` (`io.modelcontextprotocol/protocolVersion`, `…/clientInfo`, `…/clientCapabilities`); `serverInfo` in each result's `_meta` | 2575 | **Required.** Read them per request, and keep `initialize` for older clients. |
| `server/discover` returns versions, capabilities, identity | 2575 | **Required.** New method. |
| Unsupported version error `-32022` | 2575, minor 12 | **Required for a request `_meta` version.** `initialize` answers a supported version instead: an unknown one gets `2025-11-25`. The schema name is `UnsupportedProtocolVersion`, code `-32022`. |
| `resultType: "complete" \| "input_required"` on every result | 2322 | **Required.** Add `"complete"`. |
| `ttlMs` and `cacheScope` on `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` | 2549 | **Required.** `tools/list`, `prompts/list` and `server/discover` are a long public hint. `resources/list` names each object's history, so it is `ttlMs: 0` and `private`, as `resources/read` is. |
| `tools/list` does not vary per connection, in a stable order | 2575, minor 3 | **Conflicts with tool groups.** See D1. |
| `subscriptions/listen` replaces list-changed notifications | 2575 | Only if D1 keeps groups. |
| `ping`, `logging/setLevel`, `notifications/roots/list_changed` removed | 2575 | Keep `ping` for older clients only. |
| Progress notifications stay on the request's own stream | 2575 | Already so. |
| Multi Round-Trip Requests (`input_required` → retry with `inputResponses`, state in `requestState`) | 2322 | **Optional.** See D3. |
| Tasks become the `io.modelcontextprotocol/tasks` extension (`tasks/get` to poll, `tasks/update`, `tasks/cancel`) | 2663 | **Done (M3).** A 2026 client that lists the extension on the request. |
| Extensions framework (`extensions` in capabilities) | minor 1 | Advertise what D2 and D3 adopt. |
| Any JSON Schema 2020-12 keyword; `structuredContent` any JSON | 2106 | **Optional.** Nothing breaks. |
| Resource-not-found `-32002` → `-32602` | 2164 | Check `resources/read` on an unknown URI: it should answer `-32602`. |
| Roots, Sampling, Logging deprecated | 2577 | None used. |
| Header routing, SSE resumability removed, authorization | 2243, 2575, 2468… | HTTP only. None for stdio. |

## 3a. M6: the skill travels with the server

**Why.** The `lime-slice` skill teaches an agent how to work with this server: the recipe workflow, the ops that
refuse and why, assemblies, export and slicing. Until now it was one file in the owner's user folder
(`~/.claude/skills/lime-slice/SKILL.md`). It had to be copied to each machine by hand, and it fell behind each release
until someone edited it. The owner expected it to come with the MCP server.

**The mechanism.** It is not part of the 2026-07-28 core. It is the Skills extension, SEP-2640
(`modelcontextprotocol.io/seps/2640-skills-extension`, Final as an Extensions Track SEP; the extension spec is labelled
beta, and Claude and Claude Code support it in public beta). A server that declares
`capabilities.extensions["io.modelcontextprotocol/skills"]` serves its skills as resources and answers two methods:
- `skills/list` returns `{resultType: "complete", skills: [...]}`. Each entry is `{uri, frontmatter, resources}`:
  - `uri` is the SKILL.md URI.
  - `frontmatter` is the file's YAML frontmatter as JSON.
  - `resources` is every file of the skill, each as `{uri, digest: "sha256:<64 hex>", size}`, where size is the raw byte
    length.

  On 2026-07-28 the reply also carries `ttlMs` and `cacheScope`.
- `skills/get {uri}` returns `{resultType: "complete", skill: <entry>}`. A URI that is not a served skill is `-32602`.

The files use `skill://<skill-path>/<file>` URIs, and the last segment of `<skill-path>` must equal the frontmatter
`name`. The extension requires the `resources` capability, which the server already has. `directoryRead` stays off.

**The skill's source.** `mcp/skills/lime-slice/SKILL.md` in this repo. It is the owner's skill as it stands at
7.4.1, shipped as is (D5). `tools/mcp/bundle.mjs` copies `mcp/skills/` beside `server.mjs`, so an install has it at
`%LOCALAPPDATA%\Lime Slice\mcp\skills\lime-slice\SKILL.md` (and the matching folder on macOS and Linux). From M6 on,
skill edits are PRs to that file, and a release ships the skill that describes it.

**Do (one PR, `mcp/protocol.ts` and a small `mcp/skills.ts`):**
1. Declare the extension for both revisions: in `initialize`'s capabilities (2025-11-25 and older clients) and in
   `server/discover` (2026-07-28). Use `{}` as its value, so `directoryRead` stays false.
2. `skills/list` and `skills/get`, with the shapes above. Read the files from the `skills/` folder beside the server
   (or `mcp/skills/` in a checkout). The frontmatter is parsed from the file, not hard-coded, and the server refuses
   to list a skill whose frontmatter has no `name` or `description`, or whose `name` is not the URI's last segment.
   Digests and sizes come from the bytes on disk.
3. `resources/read` answers `skill://lime-slice/SKILL.md` (and any other file of the skill) with
   `mimeType: "text/markdown"`. Whether `resources/list` names the SKILL.md is the implementer's call. It must not
   enlarge first contact.
4. Nothing goes into the server's `instructions` or the default `tools/list`. First contact (1500 tokens) is unchanged.
5. Tests in `mcp/skills.test.ts` (added to `tools/unit-tests.txt`):
   - both revisions see the extension;
   - list and get agree;
   - each digest and size match the file's bytes;
   - an unknown URI is `-32602`;
   - the frontmatter equals the file's;
   - a skill whose name and path disagree is not listed;
   - the bundle (`npm run build:mcp`) contains `skills/lime-slice/SKILL.md`.

**Verify on this machine after the release that ships it.** Install it, restart Claude Code, and check that the
`lime-slice` skill comes from the server: the client shows its origin as the lime-slice MCP server. While the owner's
local copy still exists there are two skills with one name. Removing or trimming the local copy is the owner's call,
asked for then, never done unasked.

**Result on 7.4.2 (2026-11-26).** The installed server declares the extension and answers `skills/list`, `skills/get {uri}` and `resources/read` with the release's SKILL.md. Claude Code 2.1.332 does not use it: its capabilities list only the tasks extension (§1), and a fresh session with the owner's local copy moved aside had no `lime-slice` skill. The server side is done. Until a Claude Code release lists `io.modelcontextprotocol/skills`, the local copy stays, and it is still copied by hand.

**Reach without the extension (2026-11-27).** A headless Claude Code 2.1.312 session against the bundled server asked only `server/discover`, `prompts/list`, `resources/list` and `tools/list`, and declared only the tasks extension. So the server also gives each skill as a prompt and names its SKILL.md in `resources/list`. In that session the prompt is the slash command `/mcp__lime-slice__lime-slice`, and `resources/list` carries `skill://lime-slice/SKILL.md`. Nothing was added to `instructions`: one sentence there took first contact from under 1500 tokens to 1537. A slash command is typed by the user; the model does not load the skill by itself this way.

**What the maintainer inherits.** The `release` skill gets one step from M6 on: before the bump, check that
`mcp/skills/lime-slice/SKILL.md` describes the release (its stage keys, tools and version notes), and fix it in a PR
of its own if not.

## 4. Out of scope

- **An HTTP transport.** The server is local and one process per client; HTTP would bring authorization and shared
  state for no user benefit. If a remote use appears, it gets its own plan.
- **Moving the server onto SDK v2.** The handler is small and covers exactly what Lime Slice uses. The SDK is used in tests to
  prove compatibility, not adopted as the server.

## 5. Decisions

D1 to D4 were approved by the owner on 2026-11-25 as recommended. D5 was the owner's decision on 2026-11-26.

- **D5. The shipped skill's content.** The repo is public, and the skill ships in every installer. The skill is
  mostly a general how-to, but a few lines are the owner's own setup: the Ideaformer IR3 V2 as the print target, and a
  routine of git for each project and a `notes/LESSONS.md`. The owner chose to **ship it as is**, rather than split
  those lines into a local skill or drop them.

- **D1. Tool groups.** The 2026 revision expects `tools/list` to be the same for every connection, and groups change
  it mid-session. Recommended: for a 2026 client, list the discovery tools only and never send `list_changed`. A call to
  any tool already runs whether its group is open or not, and `guide` finds every tool. Older clients keep groups as
  today.
- **D2. Tasks for long jobs.** Recommended: yes, as M3. Clients that understand tasks poll natively instead of learning
  `slice_wait`. `slice_wait` stays.
- **D3. Input requests.** Recommended: not now. Nothing in Lime Slice waits for a person mid-call: refusals say what to
  change, and `probe: true` is an argument. Revisit if a confirmation (for example before overwriting an export) is
  wanted.
- **D4. SDK v2 in tests.** Recommended: add it in M5 once a stable v2 release is published. The June packages were
  beta, and a stable v2 was not confirmed when this was written.
